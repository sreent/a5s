# Rent the plumbing, own the governance kernel

As of October 2026, none of the three cloud platforms implements the part of the lean framework that makes it distinctive, and neither does LangChain Deep Agents. That part is a policy model: attribute owners approve autonomy per agent, per part of a domain and per change type in the domain profiles; a never-list from the charter is checked against live sensitive-field lists; every level-1 proposal gets its own human decision with a measured review time; agents move up a level only on sampled evidence; and the data team that builds the agents can never approve them. What Microsoft (Agent 365, Entra Agent ID, Purview, Defender, Foundry), AWS (Bedrock AgentCore) and Google (Gemini Enterprise Agent Platform) did converge on during 2026 is the plumbing those rules need: an identity per agent with a named human sponsor, a registry with approval states, a gateway that denies by default and checks every tool call outside the agent's code, OpenTelemetry tracing and managed evaluations. Deep Agents (0.7.32, still pre-1.0) contributes a capable agent loop with durable human-in-the-loop interrupts, but its safety controls run inside the agent process, allow by default, and have already had approval-bypass advisories. a5s should therefore rent identity, sandboxing, gateway enforcement and telemetry from whichever cloud hosts it, and build a thin, portable governance kernel itself: a register that carries the lean fields, a policy pack that encodes R-18, R-21 and R-22 against the domain profiles and fails closed, an approval bridge into the unified app, a tamper-evident evidence ledger, masking driven by data classification, and measures that expose rubber-stamping. For long-lived agents such as the governance coordinator and the owner assistant, Nous Research's Hermes Agent shows how an agent can "live" through an always-on gateway, durable schedules, heartbeats that fire only when idle, and bounded memory; but its own security policy admits that nothing inside its process is a security boundary, and its self-written skills and self-created schedules are exactly what an estate governed by R-19 must forbid. The governed alternative is an agent that lives in records rather than in a process: its obligations are computed from the exception register and request turnaround times, events wake its compute, and every lasting change to its memory, skills or schedules is a tested release.

## Eighty requirements come down to a policy model no vendor sells

The lean framework's "Agent-operated" principle is narrow on purpose: agents "prepare, chase, route, draft and propose", while "People decide, and stay accountable" ([charter.md, Principles](https://github.com/sreent/lean-framework/blob/main/charter.md)). The register names five agents: a request assistant for requesters, an owner assistant for attribute owners and their delegates, a quality agent for attribute owners, a governance coordinator for the GPDOs and the platform owner, and a change reconciler for internal controls ([operating-model.md, Agents](https://github.com/sreent/lean-framework/blob/main/operating-model.md)). Four start at **level 1**, where they propose and "The attribute owner or their delegate approves each one"; the change reconciler starts at **level 0** and only reports; and every starter domain profile sets its level-2 row to **"None yet"** ([rulebook.md, autonomy table](https://github.com/sreent/lean-framework/blob/main/rulebook.md); [baseline notes §2](../research_notes/Agent%20OS%20lessons%20from%20cloud%20platforms/baseline_scenario.md)). R-18 binds all five. Each agent "is recorded in the agent register with a named agent owner, works only within the autonomy level the attribute owner has approved for their part, and logs every action"; it changes master data "only through the unified app, at level 2"; and it must never "approve requests or exceptions, confirm sensitive changes, change sensitive fields, delete records or grant access" ([rulebook.md, R-18](https://github.com/sreent/lean-framework/blob/main/rulebook.md)). R-21 keeps trade secrets away from any AI model "outside an environment the organisation controls", which the charter defines as the organisation's own systems or "a provider's service under a contract that stops the provider keeping or training on the data". R-22 says content from outside the organisation is treated "as data to check, never as instructions" ([rulebook.md, R-21 and R-22](https://github.com/sreent/lean-framework/blob/main/rulebook.md); [charter.md, Controls we never switch off](https://github.com/sreent/lean-framework/blob/main/charter.md)).

The baseline analysis turned these rules into **80 platform requirements, AOS-01 to AOS-80, in eleven groups**: 44 stated directly in the framework documents, 24 that pair a stated rule with an inferred mechanism, and 12 that are inference ([baseline notes §9](../research_notes/Agent%20OS%20lessons%20from%20cloud%20platforms/baseline_scenario.md)). The framework deliberately puts most enforcement in the unified app, which checks every request, holds sensitive changes until they are confirmed, and records the request behind every change ([operating-model.md, The platform](https://github.com/sreent/lean-framework/blob/main/operating-model.md)). That leaves the agent OS six duties of its own: identity, the never-list, the autonomy matrix, control of outbound data and of where models run, prompt-injection handling, and logging with evaluation. Five capabilities decide how much a platform really helps with them: policy checked on every tool call against outside configuration that changes often (the domain profiles); human approval that records who reviewed each item and how long it took; writes that are logged and reversible; non-human identities that can sit in access reviews; and model hosting that guarantees the provider keeps no data and does not train on it.

All three clouds now ship the same five-part control plane of identity, registry, gateway with policy, observability with evaluation, and a managed runtime. **None ships autonomy levels.** The research found no numeric autonomy scale from Microsoft, whose guidance handles autonomy through access patterns, approval tiers and runtime blocking ([CAF: govern and secure AI agents](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ai-agents/governance-security-across-organization)). Google ties oversight to classes of action, such as "critical or irreversible" ones, rather than to levels ([Google's Approach for Secure AI Agents](https://storage.googleapis.com/gweb-research2023-media/pubtools/1018686.pdf)). AWS's four-scope Agentic AI Security Scoping Matrix is a framework, not a product setting ([AWS](https://aws.amazon.com/ai/security/agentic-ai-scoping-matrix/)), and its critics argue that agency (what an agent can touch) and autonomy (whether a person approves) vary independently ([CSA](https://cloudsecurityalliance.org/blog/2025/12/16/enhancing-the-agentic-ai-security-scoping-matrix-a-multi-dimensional-approach)). The lean matrix of agent × part × change type already sets both in every cell. Treating autonomy as a setting the business owns, approved by the attribute owner "for their part", puts the lean framework ahead of every vendor, and that gap is a5s's opportunity.

## Three clouds converge on identity, registries and deny-by-default gateways

### Microsoft turns accountability into identity data

Agent 365 is a control plane, not a runtime. It reached general availability for commercial customers on **1 May 2026** at **$15 per user per month**, or inside Microsoft 365 E7 at $99, and it joins a registry in the Microsoft 365 admin center with Entra for identity, Purview for data and Defender for threats; the licence attaches to the accountable person rather than the agent ([Agent 365 overview](https://learn.microsoft.com/en-us/microsoft-agent-365/overview); [Agent 365 Licensing FAQ](https://www.microsoft.com/licensing/faqs/122)). Its first lesson is that accountability can be stored as identity data and kept current automatically. Every Entra agent identity and blueprint **must have a human sponsor**, who carries business accountability and can only disable or soft-delete the agent, while optional technical owners manage its credentials; when a sponsor leaves, sponsorship passes to their manager "to prevent orphaned agents" ([Owners, sponsors, managers](https://learn.microsoft.com/en-us/entra/agent-id/agent-owners-sponsors-managers); [Governing agent identities](https://learn.microsoft.com/en-us/entra/id-governance/agent-id-governance-overview)). The registry shows "Agents without owners" as a headline tile and supports rules that flag ownerless agents or block risky ones ([Agent Registry](https://learn.microsoft.com/en-us/microsoft-agent-365/admin/agent-registry-overview); [Agent overview in admin center](https://learn.microsoft.com/en-us/microsoft-agent-365/admin/agent-365-overview)). The lean register needs the same behaviour: the platform owner names an agent owner and a deputy, and a5s should refuse to run any agent whose owner and deputy have both gone rather than leave the gap for the next owner review to discover.

The second lesson is the split between blueprint and instance. A blueprint describes a kind of agent and its permissions, and admins can "apply a conditional access policy to all Sales Assistant Agents… disable all… revoke a permission grant for all" ([Entra: agent identities](https://learn.microsoft.com/en-us/entra/agent-id/agent-identities)). That maps cleanly onto the lean register as five blueprints, one per register entry, with an instance per domain part. Instances give the least-privilege scoping AOS-08 asks for and match the agent × part grain of the autonomy matrix, while the blueprint gives the data team one switch that suspends every instance of a misbehaving agent, something the lean documents never describe (AOS-19 is recorded as a gap). Entra Agent ID reached GA in spring 2026 (Entra's release notes say April; some third parties cite 1 May), and since July 2026 Copilot Studio creates one for every new agent with no opt-out ([What's new in Agent ID](https://learn.microsoft.com/en-us/entra/agent-id/whats-new-agent-id); [Copilot Studio what's new](https://learn.microsoft.com/en-us/microsoft-copilot-studio/whats-new)). It also serves agents built elsewhere: Microsoft documents a sidecar for "Local LLMs such as Ollama with LangChain", and the Agent 365 SDK supports the LangChain SDK on any cloud ([Integrate third-party agents](https://learn.microsoft.com/en-us/entra/agent-id/configure-third-party-agents); [Agent 365 SDK and CLI](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/)).

The third lesson is to reuse existing compliance tooling by treating the agent as a user, while knowing where that leaks. Purview audits "All agent-to-human, human-to-agent, agent-to-tools, and agent-to-agent interactions", and agent instances join DLP, insider-risk and eDiscovery policies "as you would a user" ([Purview for Agent 365](https://learn.microsoft.com/en-us/purview/ai-agent-365)). Three documented gaps clash with lean rules. "Newly created content from Agent 365 doesn't inherit sensitivity labels from the source items", which contradicts R-16's rule that a report takes the highest classification of the data in it; a DLP block is invisible to the agent, so "the agent owner must actively monitor" its effects; and Conditional Access, checked when a token is issued, cannot see resources an agent reaches with an API key ([Purview for Agent 365](https://learn.microsoft.com/en-us/purview/ai-agent-365); [Conditional Access for agents](https://learn.microsoft.com/en-us/entra/identity/conditional-access/agent-id)). Purview labels also cover Microsoft 365 content, not SAP master-data fields, so the lean classification scheme, which lives in the domain profiles, still needs its own enforcement.

Defender's real-time protection for Copilot Studio is the clearest example of a policy decision point that sits outside the agent and answers before each action: the orchestrator sends the planned tool, topic or knowledge action and its parameters to Defender, which returns allow or block, and third-party providers can plug into the same hook ([Microsoft Security blog, 23 Jan 2026](https://www.microsoft.com/security/blog/2026/01/23/runtime-risk-realtime-defense-securing-ai-agents/); [Visual Studio Magazine](https://visualstudiomagazine.com/Articles/2025/09/08/Copilot-Studio-Adds-Near-Real-Time-Security-Controls-for-AI-Agents.aspx)). What happens on a timeout is undocumented, and the research found no evidence that the hook covers SDK or Foundry agents. Microsoft's guidance is as useful as its products. The Cloud Adoption Framework says a baseline "sets the minimum requirements that every agent must meet before it is allowed to operate", and tells organisations to "avoid creating parallel governance models", to "decide in advance how to quickly disable an agent", and to "start with monitoring rather than immediate restrictions" ([CAF](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ai-agents/governance-security-across-organization)). Version 2.0 of the AI Red Team's failure-mode taxonomy (4 June 2026) found that **"HitL bypass was the most consistently exploited failure mode"**, and recommends basing approval prompts on the actual tool calls rather than the agent's description of them, tiering approvals "by reversibility and blast radius", and watching for consent fatigue ([Microsoft Security blog, 4 Jun 2026](https://www.microsoft.com/en-us/security/blog/?p=147942)). Consent fatigue is the lean framework's rubber-stamping warning under another name, which makes the operating model's measure ("Almost no rejections combined with very short reviews") a security control as well as a performance metric.

The caveats are real. Agent user accounts with their own mailboxes, and Agent 365 registry sync with Bedrock and Google, were still public preview at the May GA ([Microsoft Security blog, 1 May 2026](https://www.microsoft.com/en-us/security/blog/2026/05/01/microsoft-agent-365-now-generally-available-expands-capabilities-and-integrations/)). A practitioner who governed a LangChain agent on AWS found that the sync gave inventory only, with no Entra identity, no caller enforcement and no per-request audit, that it relied on a long-lived AWS access key, and that LangChain instrumentation can fail to attach silently ([Raj Penchala](https://www.rajpenchala.com/articles/governed-langchain-agent-on-aws)). Microsoft's own blog and another practitioner disagree about whether autonomous agents acting with their own access were GA at launch ([Ragnar Heil](https://ragnarheil.de/microsoft-agent-365-what-it-cant-do-yet-limitations-you-need-to-know/)). For hosting, Foundry hosted agents reached GA on 9 July 2026 with one sandbox per session, and they run LangGraph and LangChain projects unchanged ([Foundry July–August 2026](https://devblogs.microsoft.com/foundry/whats-new-in-microsoft-foundry-july-august-2026/); [Host LangGraph agents on Foundry](https://learn.microsoft.com/azure/foundry/how-to/develop/langchain-hosted-agents)).

### AWS moves enforcement outside the agent's code

AgentCore's central lesson is about where controls live. AgentCore Policy, GA since **3 March 2026**, attaches deny-by-default Cedar policies to a Gateway that "intercepts all agent traffic … and evaluates each request … before allowing tool access", using the user's identity and the tool's input parameters, and AWS states the purpose plainly: "By moving security controls outside of agent code … reducing the risk of policy bypass through agent manipulation" ([Policy docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy.html); [AWS News Blog](https://aws.amazon.com/blogs/aws/amazon-bedrock-agentcore-adds-quality-evaluations-and-policy-controls-for-deploying-trusted-ai-agents/)). Since June 2026 a Runtime can be set to accept invocations only from its gateway, closing the obvious way around it, and the Identity token vault releases credentials only on proof of workload identity, re-checking every request "to protect end-user data from malicious or misbehaving agent code" ([Release notes](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/release-notes.html); [Identity features](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/key-features-and-benefits.html)). The IETF's consolidated agent-identity draft states the same principle as a rule: the LLM must never have access to agent or tool credentials ([draft-ietf-wimse-aims](https://datatracker.ietf.org/doc/html/draft-ietf-wimse-aims)). For a5s, the never-list in AOS-30, which the charter says "can't be waived", therefore cannot live only in a prompt or in LangChain middleware.

AWS also shows how far rules over time can go, and where they stop. **Dogwood**, an open-source, Cedar-compatible language launched on 6 August 2026, adds clauses such as `formerly`, `count_within` and `sum_within`, so a policy can allow a payment only if an approval on the same claim happened within the past hour, or cap totals per hour ([AWS Open Source Blog](https://aws.amazon.com/blogs/opensource/introducing-dogwood-runtime-verification-for-ai-agents/); [Temporal policies](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-temporal.html)). That suits both "approval must precede action" and the lean mass-change cap (AOS-34). But the history is scoped to a policy session whose ID "is supplied by the caller", "starting a new session begins a new count", windows run to at most 24 hours, and an engine holds at most 20 such policies ([Temporal policies](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-temporal.html); [Quotas](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/bedrock-agentcore-limits.html)). An agent that split a 200-record clean-up into four runs on four days would pass every check, so blocking split runs has to rest on a ledger a5s owns, keyed by agent, part and change type. Gateway rate limits show the same trade-off: `rate=0` works as an emergency block, but rate limiting "fails open on transient errors" ([Release notes](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/release-notes.html)), which is acceptable for cost control and unacceptable for a charter control.

Other AWS patterns transfer well. Every Runtime configuration change creates an immutable version that endpoints point at, which yields the release records R-19 asks for and turns rollback into moving a pointer ([Runtime: how it works](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-how-it-works.html)). AWS Agent Registry (preview 9 April 2026, GA August 2026) catalogues agents, tools, MCP servers and skills through draft, pending-approval and discoverable states, with hooks for existing approval workflows and custom fields for ownership and compliance status ([AWS ML Blog](https://aws.amazon.com/blogs/machine-learning/the-future-of-managing-agents-at-scale-aws-agent-registry-now-in-preview); [Release notes](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/release-notes.html)). Practitioners complain that any edit sends a record back to draft ([Interview Kickstart](https://interviewkickstart.com/blogs/articles/aws-just-launched-an-agent-registry-what-engineers-need-to-know-about-governing-ai-agents-at-scale)), which is exactly the re-approval R-19 wants; but the research found no documentation that registry state controls whether Gateway will let an agent run, so the pre-start gate (AOS-13) still needs wiring. Evaluations (GA 31 March 2026) can score agents hosted anywhere from their CloudWatch logs, against ground truth that includes expected tool sequences ([AWS News Blog](https://aws.amazon.com/blogs/aws/amazon-bedrock-agentcore-adds-quality-evaluations-and-policy-controls-for-deploying-trusted-ai-agents/); [Release notes](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/release-notes.html)).

AgentCore is also the best-documented home for Deep Agents. AWS has published Deep Agents deployments since September 2025; in April 2026 AgentCore Code Interpreter became "the first AWS-native sandbox provider" in the Deep Agents framework, and `AgentCoreMemorySaver` stores LangGraph checkpoints ([AWS ML Blog](https://aws.amazon.com/blogs/machine-learning/running-deep-research-ai-agents-on-amazon-bedrock-agentcore); [Release notes](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/release-notes.html); [Memory with LangGraph](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory-integrate-lang.html)). The price is ephemeral compute: sessions run in microVMs that end after 8 hours by default (up to 14 days on the Instances compute type added in August 2026), and Honeycomb found that routing a session to a new version meant "we were losing history on every deploy" ([Runtime sessions](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-sessions.html); [Honeycomb](https://www.honeycomb.io/blog/prototype-production-aws-agentcore)).

### Google binds policy to a registry and a verified identity

Google takes the strongest line on identity. Each agent gets "a unique, strongly attested cryptographic identity" in SPIFFE form, with X.509 certificates valid for 24 hours, tokens bound to those certificates, no long-lived keys and no impersonation; when an agent acts for a user, "logs show both the agent's and the user's identities", which delivers AOS-07 out of the box ([Agent Identity overview](https://docs.cloud.google.com/iam/docs/agent-identity-overview)). Agent Identity reached GA on 22 April 2026 ([Agent Platform release notes](https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes)). Two pitfalls matter for a register that must survive redeployment: deleting an agent leaves its IAM grants behind as inactive bindings, and a redeployed replacement gets a new principal whose roles must be granted again ([Agent Identity overview](https://docs.cloud.google.com/iam/docs/agent-identity-overview)). a5s should key its register on its own stable agent ID, record the cloud principal as a changeable attribute, and re-run access reviews (AOS-05) whenever it changes.

The second Google lesson is to make the registry the source of truth and the gateway the enforcer. Agent Gateway and Agent Registry both reached GA on **18 June 2026**: "All connections are blocked by default unless an explicit IAM policy grants access", policies link an agent identity to approved Registry entries, and binding a policy to an unregistered resource fails with `NOT_FOUND` ([Agent Gateway overview](https://docs.cloud.google.com/gemini-enterprise-agent-platform/govern/gateways/agent-gateway-overview); [Assign identity and IAM](https://docs.cloud.google.com/gemini-enterprise-agent-platform/govern/policies/assign-identity-iam)). Of the three vendors, this comes closest to the lean pre-start gate, because an unregistered agent or tool simply cannot be reached. Outbound rules can also be written over tool attributes such as ReadOnly and Destructive instead of tool names ([Assign identity and IAM](https://docs.cloud.google.com/gemini-enterprise-agent-platform/govern/policies/assign-identity-iam)), which argues for labelling the unified app's agent-facing operations with risk attributes so one policy covers each new tool.

Google is explicit that controls with fixed answers and controls based on model judgement belong in different tiers. Its secure-agents paper by Díaz, Kern and Olive places a runtime policy engine outside the model that can allow, block or require confirmation, and warns that defences based on model reasoning are "non-deterministic and cannot provide absolute guarantees" ([Google's Approach for Secure AI Agents](https://storage.googleapis.com/gweb-research2023-media/pubtools/1018686.pdf)). The products follow that split. IAM denies by default; Model Armor screens content but looks at one turn at a time and does not decode Base64 ([Model Armor overview](https://docs.cloud.google.com/model-armor/overview)); and Semantic Governance Policies, which let admins write plain-language constraints that an LLM checks against the user's intent, are in preview, with a security reviewer noting that Google calls their verdicts probabilistic ([release notes](https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes); [AccuroAI](https://accuroai.co/blog/gemini-enterprise-managed-agents-security-review)). The lean never-list belongs only in the first tier.

Google also has the most developed picture of agents as coworkers. The Gemini Enterprise Inbox sorts long-running agent work into "Needs your input", "Errors" and "Completed" ([Next '26 wrap-up](https://cloud.google.com/blog/topics/google-cloud-next/google-cloud-next-2026-wrap-up)), and at Gemini at Work on 8 October 2026 Google announced coworker agents with their own `@agents.company.com` mailboxes that act "under its own identity rather than yours", one Agent Gateway policy applied to every agent, and hard spending limits per project ([Gemini at Work 2026](https://cloud.google.com/blog/products/ai-machine-learning/welcome-to-gemini-at-work-2026)). Much of this is private preview or early access. For a LangGraph-based a5s, three limits matter most: Agent Gateway is Google-managed only for Agent Runtime and Gemini Enterprise, with self-managed modes for GKE, Cloud Run and other clouds still "coming soon" ([Agent Gateway overview](https://docs.cloud.google.com/gemini-enterprise-agent-platform/govern/gateways/agent-gateway-overview)); Google's LangGraph template sits in a preview namespace with checkpointing off by default ([Vertex AI reference](https://docs.cloud.google.com/python/docs/reference/vertexai/latest/vertexai.preview.reasoning_engines.LanggraphAgent)); and ADK's tool confirmation is "experimental" and does not work with the managed session service ([ADK tool confirmation](https://adk.dev/tools-custom/confirmation/)).

### Shared blind spots: SAP write paths, hidden model calls and churn

Three hazards cut across vendors. The first is that the convenient SAP connectors write. The AWS for SAP MCP Server (GA 1 May 2026) creates, reads, updates and deletes S/4HANA and ECC business objects over OData, and Foundry exposes Logic Apps connectors to SAP as MCP tools ([AWS What's New, 1 May 2026](https://aws.amazon.com/about-aws/whats-new/2026/05/aws-sap-mcp-amazon-bedrock/); [Ignite 2025 Book of News](https://news.microsoft.com/ignite-2025-book-of-news/)). Under the lean framework only the unified app's service identity, or a domain's own governed process, changes SAP master data ([operating-model.md, The platform](https://github.com/sreent/lean-framework/blob/main/operating-model.md)), so these connectors must stay read-only or stay out. Agent-to-agent paths into SAP are also immature: SAP's own reference architecture for Gemini Enterprise calling Joule agents needs a proxy agent to exchange tokens and notes that "The Agent Gateway is not yet generally available" ([SAP Architecture Center](https://architecture.learning.sap.com/docs/ref-arch/c9a3f8)).

The second hazard is model calls hidden inside managed features. The charter's test of a controlled environment is contractual, and the platforms' no-training commitments are strong: Bedrock data "is not shared with model providers, and is not used to improve the base models", and Google says customer data "is never used to train Google models" ([Bedrock security](https://aws.amazon.com/bedrock/security-compliance/); [Gemini for business](https://cloud.google.com/gemini-enterprise)). But AgentCore Memory extraction, Policy authoring in natural language and Evaluations route model calls across regions, and "CloudWatch and AWS CloudTrail logs won't specify" where the work ran; Copilot Studio warns that some external models may process data outside the geography ([Cross-region inference](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/cross-region-inference.html); [Copilot Studio what's new](https://learn.microsoft.com/en-us/microsoft-copilot-studio/whats-new)). Under R-21 and AOS-47, every managed feature that runs a model over agent data needs its own approval, not just the agent's main model. The third hazard is churn: Google renamed Vertex AI to Agent Platform in April 2026 and gave few GA dates for its October announcements ([Futurum](https://futurumgroup.com/insights/google-collapses-enterprise-ai-into-a-single-gemini-agent-at-gemini-at-work-2026/)), and a portable kernel shields a5s from that.

## Deep Agents supplies the agent loop, not the security boundary

Deep Agents is an MIT-licensed "agent harness" built on LangChain's `create_agent` middleware, with LangGraph as the durable runtime; it adds a virtual filesystem with pluggable backends, subagents, automatic offloading and summarisation of context, skills in the Agent Skills format, AGENTS.md memory, and human-in-the-loop interrupts ([Deep Agents overview](https://docs.langchain.com/oss/python/deepagents/overview)). It is still pre-1.0: **version 0.7.32 shipped on 23 October 2026** after 25 patch releases in about two months, and 0.7 changed defaults by making planning opt-in ([PyPI deepagents](https://pypi.org/project/deepagents/#history)). The harness maps onto the lean levels with little effort. Level 0 is an allowlist of read-only tools, and level 1 is an `interrupt_on` gate on every tool with side effects, with `when` predicates to gate on argument values; because a checkpointer saves state, "the run can stop and resume later, even in another process", so a proposal can wait days for an owner ([Deep Agents HITL](https://docs.langchain.com/oss/python/deepagents/human-in-the-loop); [HITL concepts](https://docs.langchain.com/oss/python/concepts/human-in-the-loop)). Skills give versioned, file-based instructions per request type, which is what AOS-16 needs to seed agents from the vendor's written working rules ([Skills](https://docs.langchain.com/oss/python/deepagents/skills)). The Agent Server adds versioned assistants that can be promoted or rolled back, cron jobs, a store with expiry times, custom authentication handlers, and MCP and A2A endpoints ([Assistants](https://docs.langchain.com/langsmith/assistants); [Authentication and access control](https://docs.langchain.com/langsmith/auth); [A2A endpoint](https://docs.langchain.com/langsmith/server-a2a)), and LangSmith sends and receives OpenTelemetry traces and offers online and offline evaluation plus annotation queues for human grading ([Trace with OpenTelemetry](https://docs.langchain.com/langsmith/trace-with-opentelemetry); [Audit logs](https://docs.langchain.com/langsmith/audit-logs)).

The details of approval matter, because AOS-22 requires a separate decision for every proposal. LangChain's default batched mode raises one interrupt per model turn and matches decisions to tool calls by position, and the documentation gives the failure itself: **"A reviewer means to approve `write_file` and reject `execute_sql`, but sends `[reject, approve]`. The `DELETE` runs"** ([HITL concepts](https://docs.langchain.com/oss/python/concepts/human-in-the-loop)). Per-call mode, added in langchain 1.4.6 on 14 October 2026, ties each decision to an interrupt ID with a response schema; LangChain recommends it for new agents, and a5s should require it. Two more behaviours matter for level 2. On resume, "any code before the interrupt runs again"; replay from an earlier checkpoint re-runs LLM and API calls, and a fork "does not roll back a thread" ([Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts); [Use time-travel](https://docs.langchain.com/oss/python/langgraph/use-time-travel)). Checkpoints are therefore no way to reverse a change: the agent owner's power to "reverse any change" has to be built as compensating requests in the unified app, and every tool has to be idempotent.

The harness's safety tools live in the library, and they are permissive. File permission rules allow anything no rule matches, cover only the built-in file tools ("Custom tools and MCP tools … are not covered"), and do not apply to sandboxes ([Permissions](https://docs.langchain.com/oss/python/deepagents/permissions)). In October 2026 two advisories hit exactly the controls an approval model relies on: GHSA-47w2-rfrr-wvq8 let an agent get around deny and interrupt rules by writing the same path in another form, in deepagents 0.5.2 to 0.7.24, and GHSA-459r-276m-w72x let chained shell commands skip approval in deepagents-acp ([GHSA-47w2-rfrr-wvq8](https://github.com/langchain-ai/deepagents/security/advisories/GHSA-47w2-rfrr-wvq8); [GHSA-459r-276m-w72x](https://github.com/langchain-ai/deepagents/security/advisories/GHSA-459r-276m-w72x)). The storage layer is exposed too: a chain disclosed by Check Point linked checkpointer SQL injection, unsafe msgpack deserialisation and RediSearch injection into remote code execution ([CSA research note](https://labs.cloudsecurityalliance.org/research/csa-research-note-langgraph-rce-chain-20260614-csa-styled/)). There is no built-in prompt-injection classifier, the PII middleware detects five regex-based types, and under the StoreBackend's legacy default namespace "all users of the same assistant share the same storage" ([Prebuilt middleware](https://docs.langchain.com/oss/python/langchain/middleware/built-in); [Guardrails](https://docs.langchain.com/oss/python/langchain/guardrails); [Backends](https://docs.langchain.com/oss/python/deepagents/backends)).

The commercial features that resemble the clouds' governance are gated or partial. RBAC with custom roles, ABAC and audit logs (administrative actions, kept 400 days) are Enterprise features; agent-based workspaces, the nearest thing to an agent inventory, exist only on LangSmith Cloud; the LLM Gateway with spending and PII policies is in beta; self-hosted Agent Servers have "No default authentication"; and the only inbox for approvals across agents sits in the proprietary Fleet product ([RBAC](https://docs.langchain.com/langsmith/rbac); [Agents](https://docs.langchain.com/langsmith/agents); [LLM Gateway](https://docs.langchain.com/langsmith/llm-gateway); [Fleet access and oversight](https://docs.langchain.com/langsmith/fleet/access-and-oversight)). Managed Deep Agents, the route LangChain now recommends, is a US-only public beta in which "A caller with API access to the LangSmith workspace can read and search every thread" ([MDA public beta](https://langchain.com/blog/managed-deep-agents-is-now-in-public-beta); [MDA identity](https://docs.langchain.com/langsmith/python/managed-deep-agents-identity)), which would show case packs containing Restricted bank data to the data team, against R-16. The upside is portability: a deep agent is a compiled LangGraph graph that runs on AgentCore Runtime, on Foundry hosted agents through `langchain-azure-ai`, and on Google's runtime, each adding its own identity and isolation ([Host LangGraph agents on Foundry](https://learn.microsoft.com/azure/foundry/how-to/develop/langchain-hosted-agents); [AWS ML Blog](https://aws.amazon.com/blogs/machine-learning/running-deep-research-ai-agents-on-amazon-bedrock-agentcore)). A practitioner review states the right stance: Deep Agents "provides security controls, but it does not create a security boundary by itself", and "An agent must never be the only control between a model output and a payment, deletion or external message" ([Wavect review](https://wavect.io/blog/langchain-deep-agents-review/)).

## a5s must own ten components that only fit the lean framework

The evidence points to a clear split: rent the mechanisms, own the meaning. The clouds supply identity, sandboxes, gateways, telemetry pipelines and evaluation runners, but nothing on the market encodes who may approve what under the lean framework. The choice of cloud then follows the organisation's identity estate more than features. In a Microsoft 365 shop, Entra Agent ID and the Agent 365 SDK give a LangChain agent hosted anywhere an identity and Purview audit; AgentCore has the most mature out-of-process tool policy and the best Deep Agents integration; Google has the strongest identity attestation, but its gateway does not yet cover runtimes the customer manages. The ten components below are the ones a5s has to own whichever cloud it uses.

**The register and the autonomy matrix are different objects.** Today the register is a section of the operating model ("This is the agent register (R-18)"), approved by the platform owner ([operating-model.md, Agents](https://github.com/sreent/lean-framework/blob/main/operating-model.md); [baseline notes, AOS-12](../research_notes/Agent%20OS%20lessons%20from%20cloud%20platforms/baseline_scenario.md)); a5s should keep it as code, approve changes under the operating model's process, and push it to whichever cloud registry handles discovery and gateway binding. The autonomy matrix belongs to the attribute owners: level-2 change types are a domain-profile setting that "changes only with its owner's approval, which the app logs" ([controls.md, preamble](https://github.com/sreent/lean-framework/blob/main/controls.md)). a5s should read it live and never keep a copy, because a stale copy is a setting nobody approved; and while profiles are still documents and agents "never create or change master data" during the transition ([delivery/transition.md](https://github.com/sreent/lean-framework/blob/main/delivery/transition.md)), the resolver must return level 1 at most for every request type still with the vendor, whatever a profile says. Segregation of duties needs an explicit check as well. In Microsoft's admin center only an AI Administrator or Global Administrator can approve agent requests ([Agent overview in admin center](https://learn.microsoft.com/en-us/microsoft-agent-365/admin/agent-365-overview)), so if those roles sit with the data team, the platform's own flow would break the charter's "No one approves their own … agent"; a5s's workflow must reject approvals by data-team members for agents the data team owns. Because Microsoft's red team advises treating natural-language tool descriptions as code, and MCP leaves the integrity of tool definitions unspecified (the gap behind "rug pull" attacks that swap a definition after approval), the register should pin each tool definition by hash and treat a changed definition as an agent change under R-19 ([Microsoft Security blog, 4 Jun 2026](https://www.microsoft.com/en-us/security/blog/?p=147942); [Invariant Labs](https://invariantlabs.ai/blog/mcp-security-notification)).

**The best form of the never-list is an agent that never holds the power.** If agent identities have no app scopes to approve, confirm, approve exceptions or grant access (AOS-73), no injected instruction can talk them into it, and the policy decision point becomes the second line of defence. It still matters, because sensitive fields, run sizes and change types have to be judged per call against the profiles. Cedar suits the policy pack: AgentCore Policy uses it, it is a CNCF Sandbox project whose specification is formally verified in Lean, and Docker's and Stacklok's MCP gateways use it ([InfoQ](https://infoq.com/news/2026/01/cedar-joins-cncf-sandbox/); [Docker MCP policy](https://docs.docker.com/ai/sandboxes/governance/reference/mcp-policy/)). The policy should be enforced twice, in a LangChain `wrap_tool_call` middleware for fast, explainable denials inside the loop and at the unified-app API or gateway as the boundary that holds when the harness is bypassed, as GHSA-47w2 showed it can be. It should fail closed. The log-only start that AWS and Microsoft recommend should apply only to new rules that are not charter controls, because the charter's controls "can't be waived by exception".

**The approval surface must be the unified app.** The operating model says decisions happen "in the app, not in meetings" ([operating-model.md, Rhythm](https://github.com/sreent/lean-framework/blob/main/operating-model.md)), so a5s should not make a vendor inbox (LangSmith Fleet, the Gemini Inbox or Outlook forms) the place where decisions are taken. It should post each interrupt as a proposal in the app and resume the thread when the app records the decision. That yields the measures almost for free: for each proposal the app knows when it was shown, who reviewed it, when they decided and the outcome, from which a5s can compute acceptance, review time and the per-reviewer rubber-stamping signal no platform offers. The IETF draft says "local UI confirmation alone is explicitly not sufficient" for agent approvals and points to out-of-band approval instead ([draft-ietf-wimse-aims](https://datatracker.ietf.org/doc/html/draft-ietf-wimse-aims)); a decision recorded by an authenticated owner in a separate system of record meets that bar.

**Evidence and masking pull against each other, and the ledger has to reconcile them.** OpenTelemetry's GenAI conventions are still at "Development" stability and have no standard attribute for the user an agent acts for or for a policy decision ([OTel agent spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md)), so a5s must add custom attributes. Self-hosted LangSmith keeps short-lived traces for 14 days by default ([Self-host TTL](https://docs.langchain.com/langsmith/self-host-ttl)), so traces cannot serve as the audit trail. The ledger should stand on its own, hold record keys and tokenised values rather than Restricted data, and recover full values through the app when a change has to be reversed.

**The request assistant needs a pipeline built for untrusted content.** It reads outside documents such as a bank letter, which carry Restricted payment data and feed sensitive bank-detail changes, the riskiest combination in the framework ([baseline notes §2](../research_notes/Agent%20OS%20lessons%20from%20cloud%20platforms/baseline_scenario.md)). Simon Willison's "lethal trifecta" of private data, untrusted content and external communication names the danger ([Simon Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)), and the design-patterns literature gives the rule that once an agent has taken in untrusted input, that input must not be able to trigger consequential actions ([arXiv 2506.08837](https://arxiv.org/abs/2506.08837)). In practice, a quarantined extraction step with no tools turns the letter into typed field proposals, every value is tagged with where it came from, and the policy refuses any value that came from the document as a verification contact, as R-15 requires. Classifiers such as Prompt Shields, Model Armor and Guardrails then serve as signals, not as the boundary.

The comparison also exposes rules the lean documents lack. They describe no way to switch off or demote an agent, set no cost caps, no log retention and no rule for agent-to-agent calls, and do not say who runs the design review or approves an agent's model ([baseline notes §3, §9](../research_notes/Agent%20OS%20lessons%20from%20cloud%20platforms/baseline_scenario.md)). The platforms show what such rules look like. The Cloud Adoption Framework says to decide in advance how to disable an agent, and Entra can disable every agent built from a blueprint in one action; Copilot Studio disables custom agents at 125% of prepaid capacity ([Copilot Studio billing](https://learn.microsoft.com/en-us/microsoft-copilot-studio/requirements-messages-management)) and Google enforces hard spending limits per project; and A2A v1.0 provides signed Agent Cards and an `INPUT_REQUIRED` state for calls between agents that need human input ([A2A specification](https://a2a-protocol.org/latest/specification/)).

## Persistent agents should live in records, not processes

### Hermes lives through five mechanisms worth copying

The intuition about Hermes Agent is right about the mechanics. Hermes is MIT-licensed, with v0.22.5 as its latest stable release on 23 October 2026 ([tag v0.22.5](https://github.com/NousResearch/hermes-agent/releases/tag/v0.22.5); [README](https://github.com/NousResearch/hermes-agent/blob/main/README.md)), and five mechanisms make it "live". Each profile runs one long-lived gateway process, installable as a systemd or launchd service with `Restart=always`, that hosts every chat surface; closing the terminal "does not cancel the turn" ([messaging setup](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/messaging/index.md); [CLI](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/cli.md)). Gateway conversations "do not reset after inactivity or at a daily boundary", so a chat "can run for weeks as a single session" ([sessions](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/sessions.md); [memory](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/memory.md)). Sessions persist in SQLite. A small curated memory pair, capped at 2,200 and 1,375 characters, is loaded as a frozen snapshot at the start of each session, while full-text search over every past session lets the agent "find things it discussed weeks ago" ([memory](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/memory.md)). And the agent schedules itself: one tool creates, pauses and edits cron jobs, webhooks can fire a job "the moment something happens", and a per-session heartbeat re-enters the conversation on a timer ([cron](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/cron.md); [webhooks](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/messaging/webhooks.md); [heartbeat](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/heartbeat.md)). Microsoft's Foundry now advertises hosting long-running autonomous agents, naming OpenClaw and Hermes, with durable state ([Foundry Build 2026 blog](https://devblogs.microsoft.com/foundry/agent-service-build2026/)). "Living" is an engineering pattern, not a property of the model.

Several of Hermes's operating habits carry over directly. The heartbeat fires only when the session is idle, merges missed ticks into one, gives way to user messages, may answer with a silent `NO_REPLY`, and carries a "don't-invent-work guard" ([heartbeat](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/heartbeat.md)). A cron run keeps its fire identity until delivery has been durably recorded, "An interrupted execution… stays paused for operator review" instead of resuming by itself, and sessions started by cron "cannot recursively create more cron jobs" ([cron](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/cron.md)). Approvals are denied by default in cron, webhook and other unattended modes because no human is present ([security](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/security.md)), and when memory write approval is switched on, background writes wait for review and each approval applies only to the exact entry reviewed ([memory](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/memory.md)). OpenClaw, which popularised the same pattern, adds delivery only to the owner within set active hours, and provenance on remembered items so that memory from untrusted sources "never reach[es] the consolidation prompt or durable promotion" ([OpenClaw heartbeat](https://docs.openclaw.ai/gateway/heartbeat); [OpenClaw memory](https://docs.openclaw.ai/concepts/memory)).

### Hermes's risks are ones a governed estate cannot carry

Hermes is candid that its model does not fit an enterprise. Its security policy describes "a single-tenant personal agent" and states that **"The only security boundary against an adversarial LLM is the operating system. Nothing inside the agent process constitutes containment — not the approval gate, not output redaction, not any pattern scanner, not any tool allowlist"** ([SECURITY.md](https://github.com/NousResearch/hermes-agent/blob/main/SECURITY.md)). Its defaults are permissive: memory write approval is off, the default `smart` approval mode lets a cheaper auxiliary model approve commands it judges low-risk, and "The agent can modify or delete any skill" while the skill linter never blocks a write ([memory](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/memory.md); [security](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/security.md); [skills](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/skills.md)). An outside audit of v0.8.0 found **4 Critical and 9 High issues in the default configuration**, including "skill files that persist across sessions", and NeuralTrust counts **12 CVEs**, among them injection flaws in the memory scanner and the skills guard ([CSA research note](https://labs.cloudsecurityalliance.org/research/csa-research-note-hermes-agent-cves-20260504-csa-styled/); [NeuralTrust](https://neuraltrust.ai/blog/hermes-agent-security)). OpenClaw showed attackers turning the persistence channel itself into a weapon: an injection planted on a web page could "append attacker instructions to HEARTBEAT.md", a file the agent re-reads every cycle; a critical CVE let context passed into heartbeat runs escape the sandbox; and an audit of its skills marketplace found 341 malicious skills among 2,857 ([The Hacker News](https://thehackernews.com/2026/02/openclaw-integrates-virustotal-scanning.html); [GHSA-g5cg-8x5w-7jpm](https://github.com/advisories/GHSA-g5cg-8x5w-7jpm); [eSecurity Planet](https://esecurityplanet.com/threats/hundreds-of-malicious-skills-found-in-openclaws-clawhub)).

Research explains why persistence amplifies these risks. A June 2026 study of memory poisoning found that "a single adversarial write can exert long-term influence" and that agents built to write memory more aggressively are easier to exploit ([arXiv 2606.04329](https://arxiv.org/abs/2606.04329)), and a study of self-modifying agents found their safety behaviour degraded as memory accumulated and that tools they created introduced vulnerabilities ([ICLR 2026, "Your Agent May Misevolve"](https://proceedings.iclr.cc/paper_files/paper/2026/hash/a24cd16bc361afa78e57d31d34f3d936-Abstract-Conference.html)). OpenClaw removed its most autonomous proactive feature, "inferred commitments" (follow-ups the model extracted from conversations and pursued through the heartbeat), in v2026.8.1 ([OpenClaw automation](https://docs.openclaw.ai/automation)). Persistence also costs money: a single session running for weeks "grows expensive" ([memory](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/memory.md)), and Copilot Studio bills each recurring trigger as a message while running autonomous triggers on the maker's credentials, so the agent's users may "access data and systems using that same authorization" ([Copilot Studio triggers](https://learn.microsoft.com/en-us/microsoft-copilot-studio/authoring-triggers-about)). Each of these habits breaks a lean rule. Self-written skills are changes to an agent's instructions, which R-19 says are "tested before release"; free-text memory that collects bank details is an unapproved extract of Restricted data "outside live systems" under R-16; a second model approving actions is not "The attribute owner or their delegate approves each one"; schedules the agent creates for itself change what it does without a register change; and a maker's credentials behind an autonomous trigger break the record of agent and principal that AOS-07 requires.

### A governed chaser takes its obligations from the registers

The cloud runtimes have already rejected the process that lives forever. AgentCore microVM sessions end after 8 hours by default (14 days on Instances), Google's Agent Runtime runs "continuously for up to 7 days", and Microsoft models a persistent digital worker as an identity with a sponsor, a server-to-server mode "for scheduled tasks, monitoring, and background processing" and, in early-access preview, an agent user account with its own mailbox ([AgentCore runtime sessions](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-sessions.html); [Google Cloud blog, 29 Jul 2026](https://cloud.google.com/blog/products/ai-machine-learning/whats-new-in-gemini-enterprise-agent-platform); [Agent 365 identity](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/identity)). LangGraph supplies the durable pieces (cron jobs bound to a thread, a long-term store, interrupts that wait for days), but expiry is off by default ("threads do not expire") and forgotten cron jobs "can generate unwanted LLM API charges" ([LangSmith cron jobs](https://docs.langchain.com/langsmith/cron-jobs); [Configure TTL](https://docs.langchain.com/langsmith/configure-ttl)). A persistent a5s agent should therefore be five governed parts, each with its own off-switch: an identity with an owner and a deputy, a register entry, an obligation ledger, triggers and schedules, and bounded memory. Compute is the only temporary part; it is woken, rehydrated from the other five, and discarded.

The obligation ledger is the key design move. For the governance coordinator, every chase target already exists as a record: exceptions "recorded with its rule, reason, approver and expiry" that expire within [TBC: 90 days] and that the coordinator reminds owners about before they lapse, fields with no owner or more than one, the owner-review pack, and the decisions it "tracks" ([rulebook.md, R-20](https://github.com/sreent/lean-framework/blob/main/rulebook.md); [charter.md, Who owns what](https://github.com/sreent/lean-framework/blob/main/charter.md); [operating-model.md, Agents](https://github.com/sreent/lean-framework/blob/main/operating-model.md)). For the owner assistant, a case is overdue once it passes the profile's turnaround time of **"2 business days for standard requests; 4 business hours for urgent ones"** ([starters/supplier.md](https://github.com/sreent/lean-framework/blob/main/domains/starters/supplier.md)). Whether a chase is due is a check with a fixed answer, and the operating model says such checks belong in the app ([operating-model.md, Agents](https://github.com/sreent/lean-framework/blob/main/operating-model.md)). a5s should compute due obligations from these records with ordinary code, store each chase (who, when, which channel, which escalation step) as a structured contact-log entry, and let the model do what it is good at: drafting the message, merging pending items into one daily digest per person, and summarising the case. That avoids the failure that made OpenClaw drop inferred commitments, and it keeps the record of who owes what in auditable data rather than in a context window an injection can rewrite.

The wake and run model should follow the same logic. The agent should wake on events where possible (a request routed, an exception nearing expiry, a decision recorded), with a Hermes-style sweep as the fallback that runs only when idle, merges missed ticks and stays silent when nothing has changed. Each wake should start a fresh thread seeded from the ledger and a frozen, versioned memory snapshot rather than extend one conversation for weeks; that caps cost, limits how long a poisoned turn can persist, and lets the evidence ledger record which memory version informed each message. Each agent instance should allow one active run at a time with idempotent tools, because LangGraph re-runs node code on resume, and Microsoft's Agent Framework has been criticised because nothing stops two processes resuming the same checkpoint and a crashed workflow looks like a running one ([Diagrid](https://www.diagrid.io/blog/still-not-durable-how-microsoft-agent-framework-and-strands-agents-repeat-the-same-mistake)). Unattended runs never approve anything; as in Hermes's unattended modes, they create a proposal and stop.

How the chaser treats people should be policy, not prompt. "At any level, agents may remind, chase and route, because that changes no data" ([rulebook.md, R-18](https://github.com/sreent/lean-framework/blob/main/rulebook.md)), so a chaser can run even at level 0 or 1, which makes the volume and content of its messages the main risk. The number of reminders each person may receive, the working hours in which they go out, and the charter's escalation chain (the request assistant first, then the attribute owner or a delegate, then the GPDO) should all be configuration. A reminder takes the classification of the data it quotes, so it should cite record keys rather than Restricted values. The chaser should send from its own identity and never from a person's mailbox (Hermes's own guide says "never hand it your personal inbox"), and it should say it is an AI, since the EU AI Act's Article 50 transparency obligations have applied since 2 August 2026 ([Hermes agent email guide](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/guides/agent-email-address.md); [Gibson Dunn](https://www.gibsondunn.com/eu-ai-act-omnibus-agreement-postponed-high-risk-deadlines-and-other-key-changes/)).

Memory, skills and retirement need the same discipline. Memory should be scoped to one agent instance and part with a single writer, because Hermes warns that two writers "will compound each other's entries into state neither of them … authored"; every entry should carry its source, be masked under R-16, expire, and be approved by the agent owner before it lands ([memory](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/memory.md)). Skills the agent proposes should be level-1 proposals to the agent owner that ship only through an R-19 release with regression tests, so nothing modifies itself in production, and long-lived agents should be re-evaluated against their regression suite on a schedule, as Google's Agent Evaluation does to detect "behavioral drift" ([Google Cloud blog, 29 Jul 2026](https://cloud.google.com/blog/products/ai-machine-learning/whats-new-in-gemini-enterprise-agent-platform)). Retirement needs its own runbook, because no platform documents one procedure that covers both deleting memory and revoking credentials and Google leaves inactive grants behind when an agent is deleted: stop the triggers, disable the identity, remove the grants, archive the evidence, and purge memory under R-17.

## Conclusion

This research turns the build question from "which platform?" into "which rules?". By October 2026 an identity per agent, registries, deny-by-default gateways and evaluation had become standard infrastructure on all three clouds, and Deep Agents runs on each of them. What is still scarce is a policy model that knows an attribute owner may approve level 2 for one change type in one part while the agent stays at level 1 everywhere else, that a price change above a threshold is sensitive, and that a reviewer who approves everything in seconds is a failing control. That model is what a5s should be. Its strongest control remains the unified app: an agent identity without the scopes to approve, confirm or grant cannot be talked into doing so, which beats any policy that blocks the call after the model has tried, and no vendor can sell that control back to the organisation.

The comparison also exposes gaps in the lean documents that should be closed before customer and supplier requests move to the unified app in December 2026. There is no rule for switching off or demoting an agent, for owner succession, for cost caps, for log retention or for calls between agents; nobody is named to run the design review or approve an agent's model; and nothing governs persistence, even though the framework expects agents to chase people for weeks. One added sentence in R-19, stating that an agent's schedules, memory and skills are part of the agent and that changing any of them is a tested release, would let a5s borrow everything that makes Hermes feel alive while keeping everything the charter says can't be waived.

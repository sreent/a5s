# The studio: build, try, publish, run and watch agents

**Status:** Steps 1 and 2 are built: the catalogue, the dashboards and each run's page, read only, with their API, a Python client, the command line, and operators' figures for the organisation's monitoring; and authoring, with drafts, the designer, the sandbox's test pane and publishing as a pull request ([progress](#progress)). Step 3, instances, is built too: the settings are in the studio, and each instance's page says what of it waits and how far it may act, takes those who approve versions of the settings to its own, and lets those who run it suspend it · **Under:** [Agent model](agent-model.md)

In code, people build and run a5s's agents with a folder for each agent, `a5s pin`, a release signed with `a5s release`, settings signed with `a5s sign`, and `a5s status` and `a5s measures` to see how they do. The studio gives the people who make and run agents what a maker studio such as Microsoft Copilot Studio gives them: one place to create an agent, try it, publish it, choose where it runs, and watch how it does. a5s's other pages, for the settings, approving, deciding, grading, the notebook and the officer, are pages of the studio now ([progress](#progress)).

It doesn't add a second way to change a5s. Everything the studio does is a change code can make too: a commit to the agents' folder, a release signed by the same people, a settings version signed by the same owners. The API comes first, and the studio is one client of it, as code, the command line and CI are.

## Progress

- [`core/studio.py`](../src/a5s/core/studio.py) works out what step 1 shows: each agent of the release with its tools and what each reads, writes or changes, and its instances; how an agent's or an instance's runs are doing, from the measures counted for those instances alone, with how runs ended, what was denied and why, and the reports sent; an instance's runs, a page at a time; and what one run did, with each tool call's decision and, for the team that runs a5s, its ledger entries. A run shows only to those who may see every record it handled: what its tools returned, what a5s's brief or a report told it, and what its trigger named, which a5s keeps with the run by key (`run_records`), for as long as the run.
- The core serves it to code, the command line and CI, behind the operators' token, `A5S_OPERATOR_TOKEN`, or the service token where a deployment sets none, under `/studio/`: `a5s agents`, `a5s agents show <agent>`, `a5s runs <instance>`, `a5s runs show <run>`, and `a5s measures --agent <agent>` or `--instance <instance>`.
- People see it on the channels app's page, `/studio/`, signed in with the organisation's identity provider, through its own API under `/studio/api/`, from the same module. The chart lets only the worker and the scheduler reach the core, so the channels app reads the figures as its own role, which migration `0044_studio.sql` grants only the columns they count and each run's own record: never what people said, what a reminder, an obligation or a question is about, or a run's token.
- The studio's pages are a React app, in [`studio/`](../studio/), with React Flow for its maps. They take their structure from a maker studio such as Copilot Studio, an agent's overview with what starts it, its tools and what it knows, and their look from a workflow tool such as n8n: each agent's page opens on a map of what starts its runs, the agent, a5s's checks, which every call passes through, and its tools, coloured by what they do, changes first. Each instance has its figures, its runs by day, in each viewer's own time zone, split by how they ended, and its runs; and each run its path, on its agent's map: what started it, each tool it called through a5s's checks, how many times, and how many of those a5s refused, with what it didn't use faded, then its calls in order. Its types are made from the API's own description, which each route's response model makes ([`core/studio_models.py`](../src/a5s/core/studio_models.py)), so a page reads each answer as the code that makes it says it is, and the studio's build type-checks every page against them ([testing](testing.md#add-a-useful-test)).
- Its packages are locked in `studio/package-lock.json`, and none runs a script of its own as it installs (`studio/.npmrc`). The image builds the pages in a Node stage of its own ([Dockerfile](../Dockerfile)) into the package, so they are the release's core, file by file, as its Python is, and the release's `build` part names what they were built from. The channels app serves them under the policy every page of a5s has: one script and one stylesheet of their own, nothing inline, and nothing from anywhere else. In a checkout, build them with `npm ci --prefix studio && npm run build --prefix studio`, on Node 20.19 or later, or without Node, as CI's tests do, with `docker build --target studio-built --output src/a5s/core/webchat/studio .`. Unbuilt, `/studio/` says how.
- Someone may watch an instance if they run it, as its owner or deputy, own its agent, own or decide for one of its parts, or approve instances; or, while it's suspended, if they approve releases, to judge whether to resume it. Of its runs, they see those whose every record they may see, and whose every document they may read, as each document names its readers; what a run read as its person, with their own permissions in another system, or in a file they sent, is theirs alone. A run takes both from the runs whose words it was given: its conversation's turns and its topic's summary, another agent's question or answer, and the past turns a search found. They see how many others there are.
- Both apps describe these endpoints in their OpenAPI documents, at `/openapi.json`.
- [`a5s.client`](../src/a5s/client.py) is the Python client for the core's API, by the operators' token, or the service token where a deployment sets none, for the team's own jobs and CI, and the command line makes its calls through it. For example, a job that reads a week of each instance's figures:

  ```python
  from a5s.client import Client

  with Client.from_env() as core:  # A5S_GATEWAY_URL and A5S_OPERATOR_TOKEN, as a5s finds them
      for agent in core.agents():
          for inst in agent["instances"]:
              figures = core.measures(days=7, instance=inst["id"])
  ```

- Operators' figures go to the organisation's monitoring as OpenTelemetry metrics ([`core/metrics.py`](../src/a5s/core/metrics.py)): the status's figures, each minute, to the endpoint the deployment names for its traces (`telemetry.endpoint` in the chart), such as a collector that passes them on to Prometheus or Azure Monitor. Each is counted by what it counts, such as an instance, a model, a tool, a trigger or an outcome, and never by a person or a record, nor with anything said. An instance's own figures go out only once it serves at least as many people as the data protection officer chose, 5 unless they choose otherwise (`data_protection.fewest_people`), since one that serves an executive alone would count their use of it; smaller ones go together, once together they serve as many. A collection reads the status once, within 5 seconds, and says first whether it could (`a5s.status.readable`), so a database that's down or hung still leaves the monitoring the 0 its runbook alerts on. The core gains no new way in: the gateway sends them out.
- The studio shows a5s's cap on a type of change only as the core sealed it, with the ledger's last word on it: the map and a version's preview say where a cap still holds a type of change to asking first. The channels app holds no seal key, so it can't check the seal itself, and what it shows decides nothing: the gateway checks each seal before a cap counts. `a5s status` shows the caps raised, as the core checks them.
- Step 2 began with its command line ([`authoring.py`](../src/a5s/authoring.py)): `a5s agent templates` lists the agents a new one may start from, a5s's blank start, the reference agents and each scenario's, saying which tools this scenario lacks for each; `a5s agent new <name> --from <template>` makes the new agent's folder from one, with its own id, a first release, its instructions, skills and test cases, and its tools pinned; and `a5s agent check` says what would stop an agent's folder from being released here: that it doesn't load as the core loads it, its budgets don't fit, its id isn't its folder's name, the scenario hasn't got a tool, a pin isn't the tool's schema now, or its model or judge isn't approved. The studio's editor runs the same checks each time it keeps a draft, as people edit it.
- Drafts ([`core/drafts.py`](../src/a5s/core/drafts.py)): the studio keeps each draft of an agent for its author, its folder file by file, through the people's API under `/studio/api/drafts`. Someone starts one from a template, for a new agent, if they own an agent or are an engineer; or from an agent's folder as released, for a change to it, if they own it or the organisation names them its author, `agent-author:<agent>` in its directory. Each time it's saved, a5s pins the tools it names that the scenario has, as `a5s pin` does, refuses files no agent's folder could hold, and says what would stop its release, by the checks `a5s agent check` makes. A draft is its author's alone to change, never in force, and gives nobody a right; the ledger records each one started and dropped, by whom. It's in its author's export, and goes when they leave or ask for what a5s keeps of them to be erased.
- The studio's editor: someone who may author an agent finds **New agent** on the agents page, names it and picks a template, and **Draft a change** on an agent's page they may change; their drafts are listed above the agents. A draft opens on its workbench, in [the designer](#the-designer): the agent on its canvas, built by hand, with what would stop its release, who would have to sign it and why, as `a5s release` works it out from what the draft changes of the agents released here, and what follows from each part of it, as they edit; and its instructions, the sandbox, and any of its files as text, beside it. Each change is kept a moment after it's made. The page changes `agent.yaml` in place, with the [`yaml`](https://eemeli.org/yaml/) package, so the definition keeps its comments and layout as its author or template wrote them, and someone can carry on in an editor. That package has no dependencies of its own, but, like TypeScript, no provenance attestation; the lockfile pins its bytes, and no install script runs.
- The test pane, in [the sandbox](#the-sandbox): once nothing would stop a draft's release and it's kept, its page has **Try it in the sandbox**. Its author says something to it as one of the scenario's made-up people, on the sandbox's stand-in model or an approved one the sandbox has the key for, and sees what it answered, each call it made with the policy's decision and why, and what the model was sent and said, whole, since everything there is made up. The studio sends the sandbox the draft's files as they were last kept, whom to be and what to say, by the token they share; this deployment's ledger records who tried which draft, as whom and on which model, but not what they said. What they said to it there, as one of the made-up people, they can keep as one of its test cases, in its `tests/tried.yaml`, which its suite runs on its model as it runs the agent's others: what was said at each step, and the tools a real model used there that a5s let it, or, on the stand-in, what was said alone, since the stand-in's choice of tools isn't the agent's. As they keep it, they can say what it must never do there, whatever it's told: the tools of its that change, write or send something it must never use, and words it must never say, which the suite and the sandbox check at each step (`avoids` and `never_says`). And where it can be right in more than one way, such as why a correction is the one to propose, they say what a right answer is, in their own words (`judged`): the agent's judge, the approved model its definition names, grades the answer right, wrong or critical beside the step's exact checks, and the step passes only if it says right. A draft whose cases ask a judge, and names none, can't be released until it does. In the sandbox, a draft tried on the stand-in is judged by it too, which thinks nothing: it looks only for the words a criterion quotes and the tools it names. On a real model, the draft's own judge judges, where the sandbox has it, and each step shows who judged it and why. A change a draft asks for there waits, as it would where people work, for its made-up deciders, who never decide it, so a case that says it asks for one can pass. What it must say they add as the other cases do. The test pane runs a draft's test cases there too, one at a time, each in a conversation of its own, on the stand-in or a real model, with the checks the agent's suite makes ([`cases.py`](../src/a5s/cases.py)): what it answered at each step, the tools it used, and whether that's as the case says, and if not, why. Where a case needs what only the suite does, such as a time to be at, records changed first, earlier turns, a decider, or a check of what a5s keeps afterwards, the pane says so, and leaves it to the suite, which runs on a stack of its own before each release is approved. On the stand-in, a case shows how the draft is wired, not what it would say. A step counts only once a run of the agent opened for it and ended in its own answer: words of a5s's own, such as that nothing serves someone or that the model isn't answering, pass none of its checks. A file of cases reads as YAML that names each key once, with no anchors or aliases, each check a list, such as `avoids: [change_due_date]`, and no key a case doesn't take, so none can look as if it checks something while checking nothing; one that doesn't read so stops the release. The suite runs every agent folder's cases, `.yaml` and `.yml`, the sample's and each scenario's, where the studio publishes them, each in its own scenario, with an instance of the agent if the settings name none ([`tests/test_agents.py`](../tests/test_agents.py)). A judge is asked with a5s's own lines first and the agent's answer last, as a JSON string, so the answer can't pass for one of them.
- [Publishing](#publishing): once nothing would stop a draft's release, its author publishes it from its page as a pull request to the agents' repository, with its folder, its pinned tools and its test cases, and a description that says what the agent may do, such as that it asks first, and who must sign its release, and why. ## What it keeps

- **The studio proposes, and people sign.** What it writes is a pull request, or the folder for one, or a draft settings version, never a change in force. Nobody gets a right through the studio that they wouldn't have at the command line.
- **It holds no keys of its own.** It acts as the person signed in. It opens a pull request as them, through the git host's own sign-in, or gives them the agent's folder to download. It holds no git token, no signing key and no way to write the settings store, so it's never an easier way round a5s than the command line.
- **The studio and the code show the same thing.** An agent is a folder in git, a release is a manifest, settings are a signed version. Someone can start an agent in the studio and finish it in an editor, or the other way round.
- **It shows people only what they may see.** Its pages come from the measures, the status, the ledger and the releases, under the same need-to-know as today. An instance's runs are for those who may watch it, such as its owner, its deputy and its parts' owners, to see, each only if they may see every record it handled. The dashboards and runs show nothing anyone said, not even by its hash, and whom a run acted for only once the data protection officer chooses it in the signed settings (`data_protection.studio_names`), as [data protection](data-protection.md) requires.

## The designer

A draft opens on a workbench, as Ocean draws one ([sreent/ocean](https://github.com/sreent/ocean)'s Workbench, FlowNode, FlowList, Picker and GateList, with nothing of the studio's own in their look): the whole window given to the work, the sidebar shrunk to its icons, and a toolbar that says which agent this is, whether what's been done is kept, how many things would stop its release, its views, Design, Instructions, Try it and Files, and its one thing to do, **Publish it**. Its first view is the designer ([`studio/src/Designer.tsx`](../studio/src/Designer.tsx)), where people build the agent by hand.

**It adopts n8n's canvas, and extends it where an agent and a5s's governance need more.** What it adopts, as n8n has worked them out:

- the canvas fills the window, with a picker of parts on the left and whatever is chosen on the right;
- each step is a square with its name beneath, joined at a dot on each side by curves, and what starts a run is rounded where nothing comes in; a long name, as a tool's often is, wraps within its step after an underscore, and every name stands clear of the curves and of the steps beside it ([`tests/test_studio_designer.py`](../tests/test_studio_designer.py));
- a part is added by dragging it from the picker onto the canvas, or with Enter on it, and a "+" on the canvas finds another;
- the canvas's one thing to do sits at its foot, **Try it**, in the sandbox, with zooming at its left;
- Delete takes the chosen step away.

What it extends:

- **An agent isn't a chain of steps.** A workflow runs in order, but an agent's model chooses which tools to call, in any order. So the canvas draws what starts its runs, the agent and its reply in a line, and hangs its model, a5s's checks and its tools below the agent from slots along its foot, as n8n hangs an AI agent's model and tools. Nobody can join tools into a sequence that would say otherwise.
- **Risk before anything runs.** Each tool's icon is in the colour of what it does: coral where it changes a record, violet where it crosses the organisation's edge, amber where it writes, blue where it reads. The picker groups the scenario's tools the same way, most consequential first.
- **a5s's checks are on the canvas**, since every call to a tool passes them.
- **What follows, for whatever is chosen**, by the settings in force and the directory as they stand: who decides its changes when it asks first, part by part, by name; the scenario's limits for each type of change; how right graded samples must show its changes in a part before a5s raises its cap there; what it may do, such as that while it reads only, a5s refuses every change; and, once each change is kept, who must sign its release and why, with who holds each role in the directory: for a new agent's owner, nobody, until the directory names someone, and its release can't be approved till then, which the draft and its pull request both say. With nothing chosen, the draft as a whole: where it stands on its way to work, what stops its release, and the same, for all of it. After each change, a line says what it made follow, such as "Added change_due_date. Unless it acts on its own, each change it asks for waits for a yes from a decider of its record's part: Ana Ortiz in billing; Omar Haddad in orders."
- **Everything an agent is, from the palette.** A new agent can start from nothing, a5s's blank start, which fits every scenario. Beside the scenario's tools, the palette offers a5s's own abilities, the preferences people set through an agent among them, and what starts its runs: a schedule, messages, what people owe in each kind of record the scenario's obligations come from, and a daily report on each, as a watcher gives, telling each person it serves what changed in their own.
- **The keyboard, and the phone.** The arrow keys move from step to step, Enter opens one, with the keyboard's focus on what it shows, and Delete takes it away. The same comes as a list, as Ocean's FlowList draws it, a choice of views away at the canvas's foot: each row opens in place, Escape closes it again with the keyboard back on its row, and a narrow screen starts with the list.

Each change is made to `agent.yaml` in place, keeping its comments, as the forms in the inspector and its files as text make theirs, and kept and checked as theirs are: one definition, and three ways to change it. A schedule's times are written in quotes, as a5s reads them.

a5s learns from how n8n solves things, and takes none of its code, words, icons or colours: n8n's Sustainable Use License allows its code only for internal and non-commercial use, which a5s, deployed by organisations, can't take on, and Ocean holds a7c, another product drawn with it, to the same. The canvas is a5s's own, on React Flow, under the MIT licence.

Whom an instance serves, the parts it works in and the agents it may ask belong to the signed settings, not the definition, which its parts' owners approve. So the designer keeps its authors' plan for its first instance with the draft, never in force: the parts it would work in, of those the settings know; whom it would serve: its author, the teams and roles the settings serve, and, by name, the people the instances its author may watch serve or are run by, so the studio names nobody of an instance they may not know of; and the instances it could ask, of those its author may see at work. The plan shows on the canvas, the agent in its parts, its messages from whom it would serve, and each instance it could ask hanging in the agent colour, and what follows narrows to it: who would decide its changes in those parts, and who would approve putting it to work there. Planning to ask another agent turns on its release's leave to ask, which its release approver signs. A co-author's copy keeps the plan, its pull request says it without naming anyone it would serve, and once its release is signed, **Put it to work in the settings** opens the settings app's form already filled in from it, for whoever may use it. Someone a plan names is in their export, and goes from it when they're erased.

### Describe it

A new agent can also start from what it's for, in its author's own words, rather than from a template: an optional start, never the end, since its author still checks and changes everything on its canvas ([`describing.py`](../src/a5s/describing.py)). The studio sends the words to the sandbox, which asks the model its author chooses, its stand-in or an approved one it has, what the agent needs of what the scenario offers: its tools, each with what it does and whether it only reads, writes, sends outside or changes records; the kinds of record people owe something in; and the abilities a description may give. The model answers with each thing it needs and why. Code then makes the draft from the blank start, never the model, and gives it the least of that: only what the scenario offers, each with the reason the model gave; reading only if it only reads, and asking first if it writes or changes anything, where each change waits for its part's decider; never acting on its own, which only the settings and graded samples give a type of change; and nothing a description can't give, such as other agents to ask or long tasks, which need the settings or a budget of their own. Whatever else the model proposes, such as what it may do or a schedule, code leaves.

The draft says, first, what it was drafted from, on which model, and each thing it was given and why, or wasn't and why not, which its author checks: they take away what it doesn't need, and add by hand what it does. The ledger records who described it, on which model, and what it was given. a5s checks the agent's name, and that its author has room for another draft of it, before it asks any model, and records each description it asks one for, by the words' hash, whatever comes of it. The stand-in thinks nothing: it gives only the tools that only read whose words match the description's, so a draft from it is a start of the fewest tools. What its author writes goes to the model they choose, as what's said in the sandbox does, and it's kept with the draft, which is theirs alone, is in their export, and goes when they leave or ask for what a5s keeps of them to be erased. Without a sandbox, a new agent starts from a template.

## The sandbox

The sandbox ([`sandbox.py`](../src/a5s/sandbox.py)) is a deployment of a5s of its own, where people try the agents they're making: `a5s sandbox`, from the same image, on a database server of its own, with its own copies of the scenario and the agents, and the scenario's made-up records and fakes.

- **It isn't the deployment people work in, whatever anyone asks of it.** It has none of that deployment's records, channels, budgets or keys: not its database's password, its service token, its seal keys or anyone's signing key. It refuses a scenario whose records aren't all made up (`data_class: synthetic`), and a database whose ledger holds a deployment's work. The studio reaches it, by a token they share, and it reaches nothing of the deployment's.
- **It signs its own settings.** When it starts, it makes keys for the scenario's made-up people, keeps the private ones in memory alone, and signs its settings with them, as the scenario's instance approvers and parts' owners would. Each draft tried there becomes an agent of its own, `try-<draft>`, with an instance that serves whoever it's tried as, and its runs go through the same core, checks and policies as any run. It checks a draft's files apart before it puts them in place, so one it refuses leaves what was there, and every other author's tries, as they were. Started again on the same database, it carries on from its last settings.
- **Its model thinks nothing, unless asked.** The stand-in looks up what it's told with the first of the agent's tools whose name begins with `search`, and says what it found: enough to see how the draft is wired, what its model is offered and sent, and what the policy decides. An approved model the sandbox has the key for, where it may reach one, says what the agent would, on the made-up records alone.
- **It works on one request at a time, and keeps no queue.** Each installs a draft and settles the sandbox's settings, so one waits for another half a minute at most, then is refused, saying the sandbox is busy. It runs a case of 20 steps at most, which the agent's suite runs otherwise, and stops one before its next step once it's taken three minutes, so the studio has its answer, with what it took, before it stops waiting. A judge grades only a step the agent answered: there's nothing of the agent's to judge in a5s's own words. The channels app, which the studio's tries go through, lets each person one try there at a time, and four at a time in all, refusing the rest at once, so tries never hold the threads its chats are answered on.
- **It keeps what's said there for an hour after it's quiet:** long enough to try a draft over a few turns, then a5s's own retention sweep takes it, on an hour, not a year, and with it what lasts where people work: a note or a preference a try kept for one of its made-up people, which would otherwise reach every other author's tries as that person, their reminders, and the changes held there, which nobody decides. Its ledger, which records each call by its arguments as masked as anywhere, and nobody's name, stays as its database does. Its people and records are made up, and so should be what's said to them, as the test pane says, since someone may still type what they shouldn't.

Beside the containers, it's an overlay of its own, with its own Postgres on a network only it reaches:

```sh
A5S_SANDBOX_TOKEN=$(openssl rand -hex 32) A5S_SANDBOX_DB_PASSWORD=$(openssl rand -hex 32) \
  docker compose -f deploy/compose.yaml -f deploy/compose.sandbox.yaml up -d
```

On Kubernetes, it's a second release of the chart, in a namespace of its own ([the chart's README](../deploy/helm/README.md#the-sandbox)).

## Publishing

An author publishes a draft from its page, once nothing would stop its release: a pull request to the agents' repository, by them, never by a5s on its own account.

- **On any git host, they open it.** The page gives its folder to download, where it goes in the repository, such as `agents/<agent>/`, where this deployment has its agents, and the pull request's title and description. The description says who drafted it, from what, what the agent may do, naming how far it may act, such as that it asks first, and who must sign the release it makes, and why, as `a5s release` works it out. If something would stop its release, the description says what, rather than that nothing would. They put the folder on a branch of their own and open the pull request with those words, on GitHub, Forgejo, GitLab or whichever host the agents' repository is on. CI runs the agent's checks and its test cases there, and its people sign its release, as for a change made in an editor. This needs nothing set up, and a5s holds no token or secret for it.
- **On GitHub, a5s can open it as them**, where the team that runs a5s sets up a GitHub App for it ([`publishing.py`](../src/a5s/core/publishing.py)). The studio shows a code, which they enter at GitHub's sign-in page, as themselves, to let the App act as them there: GitHub's device flow, which needs the App's client id alone, so a5s holds no secret for it. The channels app asks GitHub for the token it gives them, uses it for that one publish, and keeps it nowhere: not in the database, the ledger or a log. The token can do only what both the App and the person may, on the repositories the App is installed on. The pull request holds the draft's folder, its tools pinned by a5s, on a branch of its own, `a5s/<agent>-<draft>`, and nothing else of the repository; files the draft let go of go from the agent's folder. A draft keeps the folder it began from, and a publish merges it, file by file, with what's on the branch now: a file only a change merged since the draft began changed stays as merged, one only the draft changed comes in, and where both changed a file, the publish is refused, saying which, so a draft begun before someone's fix was merged never takes it back. Published again, a draft adds a commit to its branch, on from the last, never over anyone's, so its pull request shows the change a review asked for. The draft stays until its author drops it, and the ledger records who published which draft, as which pull request.

To set up the second, the team that runs a5s [registers a GitHub App](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/registering-a-github-app), with:

- the device flow on (**Enable Device Flow**), and no webhook;
- Contents and Pull requests to read and write, and nothing else;
- installed on the agents' repository alone.

Then a5s needs the App's client id and the repository: `A5S_GITHUB_CLIENT_ID` and `A5S_GITHUB_REPO`, as `owner/name` (`publishing.githubClientId` and `publishing.repo` in the chart), and `A5S_GITHUB_BASE` if its branch isn't `main`. A GitHub Enterprise server's addresses go in `A5S_GITHUB_URL` and `A5S_GITHUB_API_URL`. A publish under way lives in the memory of the channels app that started it, for the 15 minutes GitHub's sign-in code lasts ([GitHub's device flow](https://docs.github.com/en/enterprise-cloud@latest/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app)): should that app restart meanwhile, its author publishes it again.

Other hosts could open it as the person too, each its own way. [Forgejo](https://forgejo.org/docs/v15.0/user/oauth2-provider/), for one, has no device flow, but signs people in for a public application, with no secret, by its own sign-in page and PKCE, and its API commits a whole folder to a new branch in one call. That's for when someone needs it.

## People, roles and spaces

Many people share one studio: those who make agents, those who own and approve them, those who watch them work, and those who audit them. It gives none of them a permission system of its own, and has no administrator over everything.

- **Who people are, and which groups they're in, is the identity provider's.** The signed settings give its groups a5s's roles, each with a scope: a part, such as billing, or an agent ([administration](administration.md)). Joiners, leavers and access reviews happen there, and a role someone loses stops working at their next sign-in.
- **What the studio does takes effect only once the right people sign.** Drafts and pull requests propose; releases and settings, signed, decide. Nobody gets a right through the studio that they wouldn't have at the command line.
- **So its spaces are views over the roles people hold, not permissions of their own.** In tools where editing changes what runs, such as n8n's projects or Copilot Studio's environments, a space is where permissions live. Here editing changes nothing that runs, so a space is only what someone's roles let them see together:

| View | What's in it | Who's in it |
| --- | --- | --- |
| Theirs, the studio's home | What waits on them, each where they do it: versions of the settings they approve, changes agents asked for that they decide, samples to grade, the release if it needs their signature, and their tasks that wait for them. Their drafts, and what each of their roles lets them do, and what gave it them | Anyone the directory knows, with a role or without one |
| Their team's | The agents and instances their groups' roles cover, those instances' figures by need-to-know, their parts, and the drafts of agents they may author | Whoever the identity provider's group holds: there's no membership to keep in a5s |
| Everyone's | The catalogue: the agents listed for everyone, what each does, who owns it, and how to ask for it | Everyone signed in |

What someone sees of an agent comes in five layers, each from the roles they hold:

| Layer | What it shows | Who sees it |
| --- | --- | --- |
| That it exists | Its name, what it does, its owner, and how to ask for it | Anyone with a role on it, the people it serves, and everyone else only if its owner lists it for everyone, in its definition. Agents are unlisted by default: a name such as redundancy planning says too much on its own |
| How it's built | What it may do, its tools by what each reads, writes or changes, when it works, its model and how far it may act, and its map; and its making, its instructions, skills, test cases and drafts | Its owners, its authors, engineers, release approvers, auditors and assurance, read only, and anyone with `agent-viewer:<agent>`, which the settings give a group with its owner's approval. The people it serves, and those who watch its instances, see what it may do, and not its making |
| How it's doing | Its instances, how many people they serve, and their figures and dashboards | Its owners, its instances' owners and deputies, the owners and delegates of the parts its instances work in, and instance approvers |
| What it did | Each run, with the records it handled | As before: someone who may see every record the run handled |
| Changing it | Drafts, trying them, publishing; signing releases and settings | As before: its authors draft, and its owners, the parts' owners and the approvers sign |

Two choices follow from it:

- **No personal agents on real data.** People try anything in drafts and the sandbox, on made-up records. Anything that touches real records goes through its owners' signatures, even for one person: an assistant of someone's own is an instance of a released agent that serves them alone. That keeps unsanctioned agents out without stopping anyone trying things.
- **One deployment for the organisation, with a part for each team.** Another deployment only where something forces one, such as a regulator, a data region or a separate legal entity, with releases promoted from one to the next.

In order: the home, with what waits on someone and what they may do; the team's view, with an agent's owners and authors reading each other's drafts and handing them over; the five layers, with the catalogue open to everyone signed in and someone asking for an agent there as a settings change for its approvers to sign; and the agents and instances nobody owns any more, on the administrators' page. The first is built: the studio's home, at `/studio/`, says what waits on whoever signed in, and `/studio/you` each role they hold, what gave it them, the directory or a group, and what it lets them do. The catalogue moved to `/studio/agents`. The second is built too: an agent's owners and authors read each other's drafts of it, read only, copy one into a draft of their own, and hand their own over to one another, the ledger recording each copy and hand-over, and the draft keeping who drafted it before: its page says who handed it over, and its pull request names everyone who drafted it; and the catalogue lists the agents someone authors as well as those they own or watch, each saying why their roles bring it into their view, such as "you author it" or "it works in billing, which you own". Nobody else reads a new agent's draft until it's released, since nobody else authors it yet, and its author may hand it over to someone who may start new agents too: an engineer, or any agent's owner. The third is built: one function in [`core/studio.py`](../src/a5s/core/studio.py) works out the layers someone sees of each agent, and why, and the catalogue and each agent's page show it that far, to everyone signed in. An agent's definition lists it for everyone (`listed: true`). An agent's owner approves a version of the settings that gives a group its `agent-author:` or `agent-viewer:` role, as a part's owner does a part's roles. An agent someone may not know of is refused just as one there isn't, so asking about it says nothing of it (`tests/test_studio_layers.py`). Someone it doesn't serve asks for it on its page. Only those who approve versions of the settings propose one, so an ask isn't a version: it waits, on their home, on the agent's owners, the owners of the parts its instances work in and, for one in no part, the instance approvers: each may know of the agent, and one with no instance waits on its owners alone. One of them answers it with a version that serves the asker through one of its instances, the settings app's request, which its approvers approve as any version, or declines it. It ends once a version in force serves them, or they withdraw it, or nobody answers it in a month ([`core/asks.py`](../src/a5s/core/asks.py), `tests/test_agent_asks.py`). The fourth is built too: the administrators' page says what nobody answers for any more, each with what to do, an agent nobody the directory names owns, an instance that names nobody to run it or someone the directory no longer knows, and a part nobody owns (`tests/test_ownerless.py`).

## Who builds what

The development team builds tools, connectors and MCP servers, in the scenario's code. Each is reviewed, and pinned in each release with what it reads, writes or changes. The studio shows them, and an agent's owner chooses from them, but nobody makes or changes a tool in the studio.

That's where most of a new use case's work is. In the [master data](../scenarios/master-data.md) scenario, the agents' definitions were about a tenth of it. The rest was the scenario's code: its rules, duplicate matching, routing, quality measures and who may see what, with their tests. It's also where the safety is. So beside the studio, the development team needs a starter kit for scenarios, which isn't built yet: a template scenario with the common patterns already wired, and its test bench. The patterns are records that are owed, held changes, a knowledge vault and a reader for outside content. Tools from an MCP server are brought in as the scenario's own: declared in its `mcp.yaml`, with the same risk flags as any of its tools, reviewed with its release and pinned ([connectors](connectors.md#mcp-servers)).

## How it maps

| In a maker studio | In a5s |
| --- | --- |
| An agent, its instructions and topics | An agent's definition: `agent.yaml`, `AGENTS.md` and its skills |
| Knowledge | The scenario's knowledge, such as a Markdown vault, through its tools |
| Actions, connectors and MCP servers | The scenario's tools, which the development team builds, reviews and pins in each release |
| Triggers and autonomous runs | Triggers, schedules, reports and obligations, in the definition |
| The test pane | A chat with a draft agent in a sandbox deployment, and its test cases on real models |
| Publishing | A release, signed by the people the change needs |
| Channels | Teams, Slack, Matrix and the web chat, as each deployment configures them |
| Environments and solutions | Deployments, each approving its own releases, and the agents' repository |
| Analytics | The measures, the status and the ledger |
| Admin and governance | Signed settings: instances, whom they serve, their parts, what they may do there and their owners |

## Decide first

| Decision | Proposed |
| --- | --- |
| What comes first | Watching, then making, then running. A read-only catalogue and dashboards can't weaken any control, and the pilot's agent and part owners need them: without them, what they'd want to see is behind the command line. So step 1 came first. Authoring was to wait until the pilot showed owners want to change their agents themselves; it was built before the pilot began, as were instances. |
| The API | First, not last. Each step ships its API, in one OpenAPI document, with a Python client and the command line on top, before its pages, so code and CI never wait for the studio. |
| Where it lives | Pages of the channels app, as a5s's other pages are, signed in through the organisation's identity provider. No new service. |
| What the test pane runs in | A sandbox: a separate deployment of a5s, with the scenario's fakes, synthetic data and a budget of its own, as the tests run. A fake model by default, and a real model when asked. It can't reach the production deployment's records, channels or budgets, because it isn't that deployment, whatever a flag says. |
| What publishing makes | A pull request to the agents' repository, opened as the person publishing. CI runs the agent's tests and its suite on real models, and the people the release needs sign it, as now. A deployment with no git host gets a draft release to sign instead. |
| Who may author | An agent's owners, and the authors its owner names (`agent-author:<agent>`), for that agent; any agent's owner, or engineer, for a new one. A new agent's first release needs the release approver and its owner. |
| What stays in code | The trusted core, the policies, the scenario's code with its tools, connectors and MCP servers, and which models are approved. The studio shows them, and changes none of them. |
| Where figures go | Operators' figures, with no personal data in them, may go to the organisation's own monitoring, such as Azure Monitor or Prometheus. What owners see stays in a5s, under its need-to-know: a business intelligence tool would show everyone everything. |
| Templates | The reference assistant and watcher, and each scenario's agents, such as the master data assistant and watcher. |

## Build, in order

Each step ends with something running and its tests passing, and ships its API before its pages.

1. **The catalogue and the dashboards, read only.**
   - The API: each agent and instance, its release and figures, and each run. The core's, behind the operators' token, for code, the command line and CI, and the channels app's, for the people who may see them, signed in, from the same module, each in its app's OpenAPI document. The command line on top of the core's: `a5s agents`, `a5s agents show <agent>`, `a5s runs`, and `a5s measures` for one agent or instance.
   - The catalogue: each agent's definition, release and owner; its tools, with what each reads, writes or changes; its knowledge, skills, triggers, schedules, reports, budgets and channels; and its instances, with whom they serve, their parts and what they may do there.
   - A dashboard for each agent and instance, over a period of a year at most, with the instances retired within it: runs and how they ended, tokens and cost with the share cached, denials and why, held changes and their decisions, grades, chases and escalations, reports sent, and who came back. It shows the same figures as `a5s measures` and `a5s status`.
   - A page for each run: what started it, whom it acted for, each tool call with the policy's decision, and its ledger entries, as `a5s ledger` shows them.
2. **Authoring and the test pane.**
   - The API and the command line first: `a5s agent new <name> --from <template>` makes an agent's folder from a template, and the checks a definition must pass run from the command line as from the page.
   - Create an agent from a template, or copy one. Edit what it works for and does, its instructions and skills. Pick tools from the scenario's tools, each with its risk shown. Set its triggers, schedules, reports, obligations, preferences, channels, context and budgets. The definition's own checks run as people type: known tools, pinned schemas, budgets that fit.
   - Test cases: add one from a test conversation, with what an answer must and mustn't say, in the same form as each agent's test suite.
   - The test pane, in the sandbox: chat with the draft against the scenario's fakes, and see each tool call, the policy's decisions and the context the run was given. Run its test cases on a real model, with synthetic data.
   - Publish: the studio shows who must sign the release, from what changed, before anyone publishes. It opens a pull request as the person publishing, with the agent's folder, its pinned tools and its test cases, and CI runs them. Examples for CI test and publish an agent from its repository, and promote a release from one deployment to the next.
3. **Instances.**
   - The settings app, folded in: instances, whom they serve, their parts and what they may do there, owners and deputies, limits, and whom they may ask. Each change is a new settings version, which the owners of its parts sign, as now.
   - Suspend or resume an instance from its page, signed in afresh, as a5s asks today.
   - Held changes, grading, caps and the notebook: the existing pages, reached from each instance.

## Later, with evidence

- **Shadow runs** were here, until people wanted to try a new version on their real work, not on fakes. They're built: a new version answers beside the one at work, sending and changing nothing, once the data protection officer chooses to let it ([shadow runs](agent-model.md#shadow-runs)), and graders compare its answers on `/studio/shadows`.

## Done means

An agent's owner creates an agent from a template in the studio, tries it in the sandbox's test pane, and publishes it as a pull request. CI passes, the people the release needs sign it, and the owners of its parts approve an instance of it. An engineer does the same from an editor, git and the command line, and gets the same result. Both watch it on a dashboard that shows the same figures `a5s measures` prints. The studio does nothing code can't, and skips no signature.

## Tests

- What the studio publishes is the same folder, pins and manifest that `a5s pin` and `a5s release` make, byte for byte.
- Everything a page does, the API and the command line do too, and the OpenAPI document describes it.
- The studio holds no git token, signing key or way to write the settings store: a pull request it opens is the person's own.
- Only an agent's owners and the authors its owner names publish it, and any agent's owner or engineer a new one. A new agent's release still needs the release approver, and a settings change each of its parts' owners.
- The sandbox has its own database, budget and channels, and the production deployment's records can't be reached from it.
- A dashboard shows an instance's runs only to the people who may see them, and nothing anyone said. Figures sent to the organisation's monitoring carry no personal data.
- Every action in the studio is in the ledger, as the command line's are.
- Browser tests for the catalogue, the dashboards, authoring, the test pane and the settings, as every page of a5s has.

## What this doesn't change

The studio holds no authority of its own: it proposes, and people sign. Tools, connectors and MCP servers stay the development team's: built in code, reviewed, and pinned in each release. Nobody edits the trusted core, the policies or which models are approved from a page. Agents kept in code stay first class, since the studio reads and writes the same files.

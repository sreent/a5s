# Google Cloud's Enterprise Agent Platform (Gemini Enterprise, Agent Platform / ex-Vertex AI Agent Builder & Agent Engine, ADK, A2A/AP2) — state as of October 2026

Research date: 2026-10-27. Naming warning for the report writer: Google renamed these products several times. Use this map when reading older sources:
- **Google Agentspace** (Dec 2024) → folded into **Gemini Enterprise** on Oct 9, 2025.
- **Vertex AI / Vertex AI Agent Builder** → **Gemini Enterprise Agent Platform** ("Agent Platform") on Apr 22, 2026 (Google Cloud Next '26).
- **LangChain on Vertex AI** → **Vertex AI Agent Engine** (Mar 4, 2025) → **Agent Runtime** (Apr 22, 2026). Sessions, Memory Bank and Code Execution (now "Agent Sandbox") kept their names under Agent Platform.
- Oct 8, 2026 ("Gemini at Work 2026"): Google now markets the end-user product as the **"Gemini agent"** / "Gemini for business"; the product page title is "Gemini for Business: The Universal Work Agent". Docs and console still say "Gemini Enterprise".

## 1. Gemini Enterprise: what it is, launch, editions, components, governance, 2026 updates

### Takeaway
Gemini Enterprise (launched Oct 9, 2025, absorbing Agentspace) is Google's per-seat "front door" app for employees (chat, enterprise search, prebuilt agents, no-code Agent Designer, partner agent gallery, 100+ connectors) sitting on top of the consumption-billed developer platform (Agent Platform). Its governance story evolved from "visualize, secure, and audit all agents from one place" (2025) to a single control plane in which no-code and pro-code agents share one identity/security/audit model (Apr 2026), and then to per-agent cryptographic identities, coworker agents with their own Workspace accounts, one-policy-for-all-agents enforced by Agent Gateway, and per-project spend caps (Oct 2026, much of it preview/early access).

### Inferences
- Google's governance model is layered: the per-seat app provides user-facing inventory/approval/sharing workflows (request → admin approve; procurement gating; visibility filters), while hard enforcement (identity, network policy, content screening) lives in the Agent Platform control plane (Agent Identity / Registry / Gateway / Model Armor) shared by no-code and pro-code agents.
- The "agent as employee" pattern (own identity, own mailbox/Drive, audit attributed to agent, least-privilege grants approved by security admins, spend caps per project) is Google's answer to accountability; attribution is to the agent, with the delegating user also recorded where on-behalf-of auth is used (see §5).
- Many Oct 2026 capabilities are private preview / early access with no GA dates or pricing; the official edition matrix still marks no-code agent building as preview a year after launch.

### Gaps
- Official per-seat list prices for Standard/Plus/Pay-as-you-go/Frontline as of Oct 2026 could not be retrieved from Google (pricing URL 404); figures above are from 2025 press and third parties.
- No Google doc found describing a single "agent inventory" console page by that name; Google uses "full IT visibility", Agent Registry and the Agents admin page instead.
- Pricing/metering for coworker agents and the Gemini agent not disclosed (Futurum reports Google does not plan per-seat licensing for coworker agents) — [Futurum](https://futurumgroup.com/insights/google-collapses-enterprise-ai-into-a-single-gemini-agent-at-gemini-at-work-2026/)

## 2. Vertex AI Agent Engine → Agent Runtime (runtime, sessions, Memory Bank, sandbox, Example Store, evaluation, observability, identity, networking, LangGraph support, pricing)

### Takeaway
Agent Engine (GA Mar 2025) became Agent Runtime inside Gemini Enterprise Agent Platform on Apr 22, 2026. It is a managed serverless runtime that hosts ADK, LangChain, LangGraph, AG2, LlamaIndex, A2A and custom agents, with managed Sessions and Memory Bank (GA Dec 16, 2025), sandboxes (code execution, computer use, shell), evaluation/simulation/optimizer, default-on tracing (GA Jun 18, 2026), per-agent SPIFFE identities (GA Apr 22, 2026), PSC-I private networking, VPC-SC, CMEK, HIPAA. Since June 17, 2026 everything bills on three unified SKUs (vCPU-hr, GiB-hr, GiB-month), with governance services (Agent Gateway, Semantic Governance) also metered in vCPU-hr.

## 3. Agent Development Kit (ADK): architecture, HITL/tool confirmation, callbacks & plugins, multi-agent, evaluation

### Takeaway
ADK is Google's open-source, model-agnostic, code-first agent framework (Python, TypeScript, Go, Java, Kotlin), now at 2.x with a graph-based Workflow Runtime. Its control points relevant to an agent OS are: tool confirmation (experimental HITL pause/resume, incl. remote confirmation via REST), runner-level plugins (recommended for cross-agent security policy; prebuilt Model Armor, PII redaction, Tool Call Integrity signing, BigQuery analytics, OTel tracing), per-agent callbacks, and a built-in evaluation stack (trajectory, rubric, multi-turn, user simulation, conformance replays).

### Cited Findings
- ADK languages/packages: Python `google-adk`, TypeScript `@google/adk` (TS 2.0 GA announced), Go `google.golang.org/adk/v2`, Java, Kotlin; agent types: LLM agents, workflow agents (Sequential, Loop, Parallel), custom; tools: function tools, MCP (incl. agent-as-MCP-server), OpenAPI, A2A (expose and consume), Google Search grounding; models: Gemini, Gemma, Claude, OpenAI, Ollama, vLLM, LiteLLM, Apigee AI Gateway; deploy to Agent Runtime, Cloud Run, GKE or self-hosted containers — [adk.dev](https://adk.dev/)

## 4. A2A protocol, AP2, and Google's agent registry/discovery services

### Takeaway

### Cited Findings
- A2A v1.0 is the latest spec version (prior 0.3.0, 0.2.6, 0.1.0); `spec/a2a.proto` is normative; bindings JSON-RPC, gRPC, HTTP+JSON/REST plus custom; clients send `A2A-Version` header (empty = 0.3); task states SUBMITTED, WORKING, COMPLETED, FAILED, CANCELED, REJECTED, **INPUT_REQUIRED, AUTH_REQUIRED** (interrupted states); optional `tenant` field; extended Agent Card fetched via `GetExtendedAgentCard` after auth; AgentCardSignature object for signing — [A2A specification](https://a2a-protocol.org/latest/specification/)

- LF (Apr 9, 2026, one-year mark): 150+ organizations (up from 50+ in Apr 2025), named supporters AWS, Cisco, Google, IBM, Microsoft, Salesforce, SAP, ServiceNow; v1.0 = first stable spec with multi-protocol support, multi-tenancy, modernized security flows, Signed Agent Cards; integrated in Azure AI Foundry and Copilot Studio and Amazon Bedrock AgentCore Runtime; LangGraph and CrewAI agents can delegate without sharing memory; SDKs in Python, JS, Java, Go, .NET; 22k+ GitHub stars; roadmap includes "consolidation of registry efforts" and security best practices — [Linux Foundation press release](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year)

## 5. Security and data governance (identity, gateway/policy, Model Armor, VPC-SC, CMEK, residency, no-training, SDP, SCC)

### Takeaway
Google's agent control plane is: **Agent Identity** (SPIFFE-based per-agent X.509 identity, 24h certs, tokens bound via mTLS/DPoP, no SA keys, no impersonation, auth manager for 3LO/2LO credentials, logs record both agent and user) + **Agent Registry** + **Agent Gateway** (ingress/egress/agent-to-agent enforcement point, default-deny IAM Unified Access Policies, Model Armor, LLM-judged Semantic Governance Policies, custom authz) + **Model Armor** (prompt-injection/jailbreak, SDP/DLP, malicious URLs, RAI filters) + **SCC-powered Agent Security dashboard / threat & anomaly detection**, layered on standard VPC-SC, CMEK, residency and no-training commitments.

### Cited Findings

**Agent Identity** — [Agent Identity overview](https://docs.cloud.google.com/iam/docs/agent-identity-overview)
- Each agent gets "a unique, strongly attested cryptographic identity" — a SPIFFE ID `spiffe://TRUST_DOMAIN/resources/SERVICE/RESOURCE_PATH`, trust domain `agents.global.org-ORG_ID.system.id.goog`; IAM principal `principal://TRUST_DOMAIN/resources/...` granted roles directly.
- X.509 certs auto-provisioned, valid 24 hours, auto-renewed; Google Cloud access tokens are bound to the cert; direct API calls use mTLS; calls through Agent Gateway also use DPoP ("double-bound credentials"); a default Context-Aware Access policy prevents replay outside the runtime.
- vs service accounts: "not shared by multiple workloads by default, can't be impersonated, and don't allow developers to generate long-lived service account keys."
- Auth manager: central credential vault/broker for outbound tools — user-delegated 3-legged OAuth (agent acts for a user), agent's own 2-legged OAuth (recommended), API key, HTTP basic (not recommended), OIDC ID tokens via federation; automates consent flows, provides visibility into end-user access and revocation.
- Audit: "When an agent acts on a user's behalf, logs show both the agent's and the user's identities."
- Least privilege: IAM allow **and deny** policies; Principal Access Boundary policies bound reachable resources (evaluated on egress); agent identities usable as principals in VPC-SC ingress/egress rules.
- Lifecycle pitfalls: deleting an agent leaves IAM bindings as inactive grants (remove manually); a redeployed replacement gets a **new** principal (re-grant roles). Supported on Agent Runtime, Gemini Enterprise, Cloud Run (GKE not listed).
- Launch stage: Agent Identity GA Apr 22, 2026; Agent Identity API (replacing IAM Connectors API) Preview Jun 18, 2026 — [release notes](https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes)
- External/custom agents can use Workload Identity Federation principals; principal sets can target e.g. all agents in a project — [Assign identity/IAM doc](https://docs.cloud.google.com/gemini-enterprise-agent-platform/govern/policies/assign-identity-iam)

**Agent Gateway and policies** — [Agent Gateway overview](https://docs.cloud.google.com/gemini-enterprise-agent-platform/govern/gateways/agent-gateway-overview)
- Enforcement point for client-to-agent (ingress), agent-to-anywhere (egress: tools, remote MCP, SaaS APIs, downstream agents) and agent-to-agent traffic; parses MCP JSON-RPC to extract tool names/methods; governs A2A delegation/task APIs; REST/gRPC.
- "All connections are blocked by default unless an explicit IAM policy grants access" (IAM Unified Access Policies link agent identity to approved Registry entries); custom authorization engines via Service Extensions; Semantic Governance Policies; token-management/budget policies "not yet available".
- Model Armor attached to gateways scans prompts and tool responses; enriched L7 OpenTelemetry traces and access logs.
- Deployment: Google-managed for Agent Runtime and Gemini Enterprise (available); self-managed for GKE, Cloud Run and cross-cloud (Envoy) "coming soon"; up to 5,000 Registry resources per gateway instance.
- Egress IAM uses `roles/iap.egressor` with CEL conditions filterable by tool attributes **ReadOnly, Destructive, Idempotent, Open World**; policy scopes from all agents in a project to a single agent/MCP server/endpoint; recommends dry-run mode and managing policies via CI/CD; binding to an unregistered resource fails `NOT_FOUND` — [Assign identity/IAM doc](https://docs.cloud.google.com/gemini-enterprise-agent-platform/govern/policies/assign-identity-iam)
- Semantic Governance Policies (Preview Jun 29, 2026): admins write plain-language "Natural Language Constraints" per agent or per tool (incl. parameter-level, e.g. financial limits); the engine evaluates each proposed tool call against the user prompt, history and policies and denies calls that violate policy or deviate from user intent; managed engine runs in customer VPC via PSC as a regional singleton policy decision point consulted by Agent Gateway — [Semantic governance overview](https://docs.cloud.google.com/gemini-enterprise-agent-platform/govern/policies/semantic-governance-overview) (search snippet); [Pulumi registry](https://www.pulumi.com/registry/packages/gcp/api-docs/vertex/aisemanticgovernancepolicyengine/) (search snippet); [release notes](https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes)
- Agent Gateway partner integrations (Broadcom, Check Point, Cisco, CrowdStrike, F5, Okta, Palo Alto Networks, Zscaler) "preview soon" as of Next '26 — [Next '26 wrap-up](https://cloud.google.com/blog/topics/google-cloud-next/google-cloud-next-2026-wrap-up)

**Model Armor** — [Model Armor overview](https://docs.cloud.google.com/model-armor/overview)
- Screens prompts and responses, model- and cloud-agnostic; detections: prompt injection & jailbreak (inputs <3 words return NO_MATCH), malicious URLs (first 256), RAI filters (CSAM always on), Sensitive Data Protection basic (cards, SSNs, GCP credentials/API keys) or advanced (SDP templates incl. de-identification); confidence thresholds; templates + project-level **floor settings**; inspect-only vs inspect-and-block (caller enforces block); document screening (PDF/Office ≤4 MB); image screening Preview.
- Limits: single-turn only (no conversation history), does not decode Base64/hex/URL-encoded content, no audio/video. Stateless; content stored only if logging enabled; regional processing; SOC 1/2/3, ISO 27001; billed per token.
- Integrations: Agent Platform, Gemini Enterprise, Apigee, Agent Gateway, Google/Google Cloud MCP servers, networking services, LangChain; available standalone or via Security Command Center.

**Threat detection / posture**
- Agent Anomaly Detection (statistical models + LLM-as-a-judge flag unusual reasoning), Agent Threat Detection (reverse shells, known-bad IPs), Agent Security dashboard powered by Security Command Center (maps agent–model relationships, asset discovery, OS/package vulnerability scans) — [Introducing Agent Platform](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform); AI security findings for agent runtimes GA Jun 24, 2026 — [release notes](https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes)

### Inferences
- Google separates three policy types by determinism: IAM (deterministic, default-deny, attribute-aware on tool annotations), Model Armor (classifier screening of content), Semantic Governance (LLM-judged intent alignment, Preview, explicitly probabilistic) — mirroring the "hybrid defense-in-depth" in §6.

## 6. Google's published guidance on autonomy, human oversight and secure-agent frameworks (SAIF, "Google's Approach for Secure AI Agents")

### Takeaway
Google's canonical position (2025 paper by Díaz, Kern, Olive) is three principles — agents must have **well-defined human controllers**, **limited powers** (dynamic least privilege, no self-escalation, inspectable/revocable delegation), and **observable actions and planning** — implemented as a hybrid defense-in-depth: Layer 1 deterministic runtime policy engines outside the model (allow / block / require confirmation), Layer 2 reasoning-based defenses (adversarial training, guard models, plan-risk prediction), backed by continuous assurance. SAIF (2023, risk map 2024, agent focus 2025) and Office-of-the-CISO guidance add identity propagation and AI firewalls.

### Cited Findings
- Paper: "Google's Approach for Secure AI Agents: An Introduction", Santiago (Sal) Díaz, Christoph Kern, Kara Olive (Google, 2025); aims for agents "powerful, useful, and secure by default" — [Google Research page](https://research.google/pubs/an-introduction-to-googles-approach-for-secure-ai-agents/); [PDF](https://storage.googleapis.com/gweb-research2023-media/pubtools/1018686.pdf)
- Key risks: **rogue actions** ("unintended, harmful, or policy-violating actions") and **sensitive data disclosure**; "increased agent autonomy and power, which drive utility, correlate" with risk — [PDF](https://storage.googleapis.com/gweb-research2023-media/pubtools/1018686.pdf)
- Principle 1 (human controllers): systems must "reliably distinguish instructions originating from an authorized controlling user versus any other input"; for "critical or irreversible" actions (deleting large data, significant financial transactions, changing security settings) "the system should require explicit human confirmation"; agents acting for teams "need distinct identities and clear authorization models"; shared agent configs must be transparent. Controls: distinct agent identities, user consent mechanisms, secure input channels — [PDF](https://storage.googleapis.com/gweb-research2023-media/pubtools/1018686.pdf)
- Principle 2 (limited powers): "extends traditional least privilege by requiring an agent's permissions to be dynamically aligned with its specific purpose and current user intent"; "maximum permission levels must be definable and enforceable"; "agents must be prevented from escalating their own privileges"; users must be able to "inspect and revoke any authority delegated"; requires AAA for agents, verifiable agent identities, scoped OAuth tokens, sandboxing — [PDF](https://storage.googleapis.com/gweb-research2023-media/pubtools/1018686.pdf)
- Principle 3 (observable): log inputs, tools invoked, parameters, outputs and "ideally, intermediate reasoning steps", securely; characterize action properties ("read-only versus state-changing, or if it handles sensitive data") for automated mechanisms and reviewers; UIs should expose intended actions for high-risk operations — [PDF](https://storage.googleapis.com/gweb-research2023-media/pubtools/1018686.pdf)
- Layer 1 example: policy engine "blocking any purchase action over $500 or requiring explicit user confirmation via a prompt for purchases between $100 and $500", or blocking external email after processing data from a suspicious source unless the user approves; outcomes allow / block / require confirmation; acknowledged limits (hard to scale, lacks context). Layer 2: adversarial training with structural prompt conventions, guard-model classifiers, models that predict plan risk; "non-deterministic and cannot provide absolute guarantees … must work in concert with deterministic controls". Assurance: regression testing, variant analysis, red teams, VRP — [PDF](https://storage.googleapis.com/gweb-research2023-media/pubtools/1018686.pdf)
- The paper's planning questions include "What level of autonomy does the agent have in planning and selecting which plan to execute" and "Does the agent require user confirmation before executing high-risk or irreversible actions?" — [PDF](https://storage.googleapis.com/gweb-research2023-media/pubtools/1018686.pdf)
- Office of the CISO (Jan 17, 2026): "strongly advise against using service accounts that have broad access"; agents should propagate the actual user's identity and permissions to every backend tool; user authorization requires front-end auth, identity propagation, MCP and A2A authorization, IAM; prompt injection is "the new SQL injection" — deploy an AI firewall such as Model Armor; SAIF approaches: "Data is the new perimeter", "Prompts should be treated as code", "Secure agentic AI requires identity propagation"; SAIF identifies 15 AI risks mapped to controls; links SAIF "focus on agents" page — [Cloud CISO Perspectives](https://cloud.google.com/blog/products/identity-security/cloud-ciso-perspectives-practical-guidance-building-with-saif/); [SAIF focus on agents](https://saif.google/focus-on-agents)
- SAIF timeline (secondary): published 2023 with six elements; Risk Assessment and Risk Map added Oct 2024; "SAIF 2.0" with agent focus Oct 2025 — [bdemerson.com](https://www.bdemerson.com/article/saif-risk-assessment) (secondary, unverified against saif.google)
- Platform implementations of these principles: Gemini Enterprise "re-authentication for sensitive actions" — [Next '26 wrap-up](https://cloud.google.com/blog/topics/google-cloud-next/google-cloud-next-2026-wrap-up); ADK tool confirmation — [ADK](https://adk.dev/tools-custom/confirmation/); Inbox "Needs your input" — [Next '26 wrap-up](https://cloud.google.com/blog/topics/google-cloud-next/google-cloud-next-2026-wrap-up); CodeMender (Public Preview Jul 2026) enforces HITL with "mandatory manual confirmations for all disk writes and command executions by default" — [release notes](https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes)

### Inferences
- Google does not publish a numbered "autonomy levels" scale; instead it ties oversight to action risk classes (irreversible, financial, security-changing) and dynamic permission scoping.
- The paper's Layer 1 maps to IAM/Agent Gateway default-deny + tool-attribute conditions; Layer 2 maps to Model Armor, Semantic Governance Policies and Anomaly Detection.

### Gaps
- SAIF 2.0 content not verified directly on saif.google.
- No Google doc found defining formal autonomy levels (L0–L5 style).

## 8. SAP relevance (Joule ↔ Gemini Enterprise A2A, SAP connectors, data)

### Takeaway
SAP was a founding A2A contributor (Apr 2025). In Apr 2026 SAP and Google announced Gemini Enterprise as a "central hub" for multi-agent coordination with SAP's agent gateway APIs (first use case: marketing, H2 2026) plus BDC Connect zero-copy data sharing. SAP's own reference architecture (updated Oct 27, 2026) shows Gemini Enterprise → Joule agents working today only via a proxy agent on Google Agent Runtime that performs OAuth token exchange with SAP Cloud Identity Services, because SAP's Agent Gateway is not yet GA and no out-of-the-box token re-scoping exists.
